# 三类用户平台整体切片路线图

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按依赖波次交付场馆、队长、散客和平台运营四个用户面的真实旅程，同时限制并行在制品。

**Architecture:** 微信小程序承载三种普通用户目的入口和业务旅程；FastAPI/PostgreSQL 提供身份、权限、库存、订单和球局权威状态；OSS 保存场馆媒体；后置的独立 Web 后台承载平台级加盟与认领审批。每个切片必须真实可部署、状态诚实且不含生产 Fixture 才算完成。

**Tech Stack:** 微信小程序 TypeScript/WXML/WXSS、FastAPI、SQLAlchemy、PostgreSQL、阿里云 OSS、DashScope、独立 Web 管理后台。

- `已完成`：生产真实链路已经闭环并通过相应验收。

- `待开发`：依赖前序切片，尚未开始生产实现。

### A2：三种目的生产入口与“我的场馆”组合页 — 验收收口中

- [x] “我要租赁场地”进入现有真实地图旅程。
- [x] “我要找球踢”显示“即将开放”，不进入 Fixture 或虚假列表。

A2 可以在不改变 A1 数据模型的前提下先实施。创建和认领按钮只有在 A3 的真实申请接口上线后才可进入生产包；视觉预览阶段使用隔离 Fixture，不用静态成功或 Toast 冒充提交。

### A3：场馆认领、新场馆加盟与平台审核 — 验收收口中

普通小程序和独立 Web 后台共同组成一个完整垂直切片：

- [ ] 小程序支持搜索并认领已有场馆，或提交尚未收录的新场馆加盟申请。
- [ ] 新增独立申请数据和私有证明材料，不把未核验场馆提前写入公开 `venues`。
- [ ] 创建申请在提交与批准两个边界分别执行去重检查；命中已有场馆时转入认领，不复制场馆。
- [ ] 独立 Web 后台只接受平台级凭证，服务端校验 `PLATFORM_ADMIN` 或 `ONBOARDING_REVIEWER`；普通用户和场馆管理员均无权访问。
- [ ] 审核人员可以查看证明、批准或拒绝申请，并记录操作者、时间和原因。
- [ ] 批准已有场馆认领时只创建或激活目标 `venue_id` 的 `venue_memberships`。
- [ ] 批准新场馆时在同一事务中创建 `is_listed=false` 的正式 `venues` 和首位管理员 `venue_memberships`。
- [ ] 审核前、审核中和拒绝状态都诚实展示；任何申请提交都不能自动获得权限。

A3 前移到订单和球局切片之前。平台主动招商邀请与员工分级授权仍保留在后续扩展，不阻塞首个“用户申请—平台审核—获得权限”闭环。

生产数据库、私有 OSS、申请 API、小程序页面、平台审核后台和部署已经完成。剩余关闭条件是各执行一次真实 CLAIM 与 CREATE 的提交—批准—数据库核对，完成最后一轮真机/桌面按钮审核，并将验收分支集成；在这些证据完成前不标记“已完成”。

## 依赖与并行边界

- A2 的小程序视觉预览与 A3 的独立 Web 审核预览文件互不重叠，可以并行；两者均须用户视觉确认后才进入契约和后端。
- A3 的申请后端与审核后端共享状态机和数据库事务，不并行修改同一模型；契约冻结后，小程序 HTTP 集成和 Web 后台 HTTP 集成可以并行。
- B1 稳定后，B2 的前端 Artifact 与 B1 的非重叠验收可以并行；B2 后端不能绕过真实订单状态。
- C1 的前端视觉可在 B2 契约冻结后并行，真实申请后端必须等待 B2 发布模型稳定。
- D1 只在 A3 稳定后开始；它与 C 系列领域数据独立，但不阻塞当前加盟主链路。
