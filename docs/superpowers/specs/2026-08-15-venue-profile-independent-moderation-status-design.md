# 场馆资料独立审核状态设计

**日期：** 2026-08-15  
**状态：** 用户已确认方案 A（图片与介绍区域各自负责状态）

## 1. 背景与结论

真实 iPhone 上传链路已经到达 OSS、完成接口和 DashScope。一次现场任务从创建到完成约 4.2 秒，结果为 `REJECT / IMAGE_NOT_VENUE`；页面持续显示“审核中”的原因是提交后没有自动重新读取服务端状态，而不是模型仍在运行。当前页面也没有启用微信原生下拉刷新。

页面改为局部状态所有权：图片审核状态留在“场馆图片”，介绍审核状态留在“场馆介绍”。顶部全局状态只表达页面读取、权限或无法归属到单一区域的请求错误，不再作为内容审核结果的唯一入口。

## 2. 图片区域

- 每张图片独立显示 `上传中 / 审核中 / 已通过 / 未通过 / 待人工审核`。
- 已通过图片使用服务端返回的已发布 OSS URL 展示缩略图。
- 未通过图片在同一图片块中展示固定原因文案和“重新审核”。
- 审核中或待人工审核时，在图片区域提供“刷新图片状态”。
- 图片上传完成后等待 5 秒自动执行一次权威资料读取；若仍在审核，不继续轮询，保留手动刷新。
- 图片审核不禁用介绍编辑或提交。

## 3. 介绍区域

- 介绍草稿拥有独立 dirty 状态和“提交场馆介绍”按钮。
- 区域内显示 `未修改 / 提交中 / 审核中 / 已通过 / 未通过 / 待人工审核`。
- 未通过时就地展示原因和“重新审核介绍”。
- 提交完成后等待 5 秒自动执行一次权威资料读取；若仍在审核，不继续轮询，保留手动刷新。
- 介绍审核不禁用图片上传、删除、排序、设封面或重试。

## 4. 设施保存

- 固定底部按钮改为“保存场馆设施”，只提交设施草稿。
- 任一图片处于 `UPLOADING / REVIEWING / PENDING_MANUAL`，或介绍处于 `REVIEWING / PENDING_MANUAL` 时禁用设施保存，并显示文字原因。
- `APPROVED / REJECTED` 不阻止设施保存。
- 提交介绍时发送服务端权威设施值，不顺带保存本地设施草稿。
- 保存设施时发送服务端权威介绍值，不顺带提交本地介绍草稿。

现有保存 API 和版本控制继续作为服务端权威，不新增数据库结构或业务接口。若并发版本变化，重新读取权威资料，同时保留未提交的本地区域草稿。

## 5. 刷新与错误

- 页面启用微信原生下拉刷新；`onPullDownRefresh` 读取一次权威资料，并始终结束原生刷新动画。
- 自动刷新严格为每次内容提交后的单次 5 秒定时读取，不建设持续轮询系统。
- 页面离开或再次提交时取消旧定时器，避免迟到刷新覆盖新状态。
- 区域刷新失败时保留当前内容，在对应区域显示“刷新失败，请重试”；其他区域继续可操作。
- 上传、提交或保存的结果未知继续复用原幂等键确认，不能生成重复审核任务。

## 6. 最小验证

- 聚焦页面测试覆盖：图片结果局部展示、介绍独立提交、设施保存不携带介绍草稿、审核中禁用设施保存、拒绝后恢复设施保存、5 秒只自动读取一次、下拉刷新结束动画。
- 运行小程序类型检查、一次生产构建和 Fixture 泄漏审计。
- 在真实 iPhone viewport 检查状态标签、按钮文字居中、底部安全区和三个区域的独立可操作性。
- 复用当前真实审核结果验证拒绝展示；不为 UI 调整额外触发 DashScope 调用。最终通过态继续在原定唯一一次真实场馆图片验收中验证。
