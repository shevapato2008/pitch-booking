# 场馆资料独立审核状态设计

**日期：** 2026-08-15
**状态：** 用户已确认方案 A（图片与介绍区域各自负责状态）

## 1. 背景与结论

真实 iPhone 上传链路已经到达 OSS、完成接口和 DashScope。一次现场任务从创建到完成约 4.2 秒，结果为 `REJECT / IMAGE_NOT_VENUE`；页面持续显示“审核中”的原因是提交后没有自动重新读取服务端状态，而不是模型仍在运行。当前页面也没有启用微信原生下拉刷新。

页面改为局部状态所有权：图片审核状态留在“场馆图片”，介绍审核状态留在“场馆介绍”。顶部全局状态只表达页面读取、权限或无法归属到单一区域的请求错误，不再作为内容审核结果的唯一入口。

## 2. 图片区域

- 每张图片独立显示 `上传中 / 审核中 / 已通过 / 未通过 / 待人工审核`。
- 只有当前草稿整体处于 `READY / PUBLISHED` 且图片均为 `APPROVED` 时，才按服务端排序把已发布 OSS URL 映射到草稿图片；审核或拒绝期间不得只凭相同序号把上一版公开图片冒充为当前草稿。无法安全匹配时展示固定场地图占位和真实状态。审核通过并发布、下一次 GET 建立新的 `READY` 草稿后展示新缩略图。
- 未通过图片在同一图片块中展示固定原因文案和“重新审核”。
- 审核中或待人工审核时，在图片区域提供“刷新图片状态”。
- 图片上传完成后等待 5 秒自动执行一次权威资料读取；若仍在审核，不继续轮询，保留手动刷新。
- 图片审核不禁用介绍编辑或提交。

## 3. 介绍区域

- 介绍草稿拥有独立 `descriptionDirty` 状态和“提交场馆介绍”按钮。
- 区域同时表达本地草稿和服务端审核状态：操作进行中优先显示“提交中”；有本地修改时显示“有未提交修改”，并在其下保留服务端的 `审核中 / 已通过 / 未通过 / 待人工审核` 状态。
- 介绍处于 `REVIEWING / PENDING_MANUAL` 时仍可编辑并积累本地草稿，但不能再次提交介绍；其他区域继续可操作。审核结束后，未修改时可“重新审核介绍”，已修改时可“提交修改”。
- 未通过时就地展示原因；无本地修改时显示“重新审核介绍”，有本地修改时显示“提交修改”。
- 提交完成后等待 5 秒自动执行一次权威资料读取；若仍在审核，不继续轮询，保留手动刷新。
- 介绍审核不禁用图片上传、删除、排序、设封面或重试。

## 4. 设施保存

- 设施草稿拥有独立 `facilitiesDirty` 状态。设施选择控件在内容审核期间仍可编辑并保留本地草稿；固定底部按钮改为“保存场馆设施”，只提交设施草稿。
- 任一图片处于 `UPLOADING / REVIEWING / PENDING_MANUAL`，或介绍处于 `REVIEWING / PENDING_MANUAL` 时禁用设施保存，并显示文字原因。
- `APPROVED / REJECTED` 不阻止设施保存。
- 提交介绍时发送服务端权威设施值，不顺带保存本地设施草稿。
- 保存设施时发送服务端权威介绍值，不顺带提交本地介绍草稿。
- 介绍提交成功只清除 `descriptionDirty`，设施保存成功只清除 `facilitiesDirty`。任何权威刷新、版本冲突或另一区域提交都保留未提交的区域草稿。

现有保存 API 和版本控制继续作为服务端权威，不新增数据库结构或业务接口。若并发版本变化，重新读取权威资料，同时保留未提交的本地区域草稿。

### 4.1 区域状态与操作矩阵

| 区域 | 权威状态或本地状态 | 可编辑 | 可提交/保存 | 状态与错误落点 |
| --- | --- | --- | --- | --- |
| 图片 | `UPLOADING / REVIEWING / PENDING_MANUAL` | 介绍、设施及其他图片操作继续可用；当前忙碌图片不可重复操作 | 当前图片不可重复提交 | 当前图片块；区域内提供刷新 |
| 图片 | `APPROVED / REJECTED` | 可用 | 拒绝项可重新审核 | 当前图片块；拒绝原因就地展示 |
| 介绍 | 本地 `descriptionDirty`，权威非审核中 | 可编辑 | “提交修改”可用 | 介绍区域同时显示本地修改和权威状态 |
| 介绍 | 权威 `REVIEWING / PENDING_MANUAL` | 可编辑并保留草稿 | 介绍提交禁用 | 介绍区域；提供刷新 |
| 介绍 | 权威 `REJECTED` | 可编辑 | 无修改时重新审核；有修改时提交修改 | 介绍区域；原因就地展示 |
| 设施 | 任一内容为 `UPLOADING / REVIEWING / PENDING_MANUAL` | 可选择并形成 `facilitiesDirty` | 底部保存禁用 | 底部文字说明阻塞原因 |
| 设施 | 内容均非审核中 | 可选择 | 仅 `facilitiesDirty` 时可保存 | 底部按钮反馈提交结果 |

## 5. 刷新与错误

- 页面启用微信原生下拉刷新；`onPullDownRefresh` 读取一次权威资料，并始终结束原生刷新动画。
- 图片上传完成、图片重新审核、介绍提交完成或介绍重新审核后，各自在 5 秒后安排一次权威读取；不建设持续轮询系统。
- 图片区域在存在 `UPLOADING / REVIEWING / PENDING_MANUAL` 或图片刷新错误时显示手动刷新；介绍区域在存在 `REVIEWING / PENDING_MANUAL` 或介绍刷新错误时显示手动刷新。
- 页面离开或同一区域再次提交时取消该区域旧定时器，避免迟到刷新覆盖新状态。
- 所有刷新调用同一个 GET 并更新全部权威区域；本地介绍和设施草稿始终保留。触发来源只决定加载/失败提示落在图片区域、介绍区域或用户主动下拉的顶部页面提示。任一成功 GET 清除两个区域的旧刷新错误。
- 上传、介绍提交或设施保存的结果未知继续复用原幂等键确认，不能生成重复审核任务。前端持久化的 `save` attempt 增加本地 `scope: description | facilities` 标识（HTTP 请求体忽略该字段），以便重试成功后只清除对应 dirty 状态并把错误放回对应区域。

## 6. 最小验证

- 聚焦页面测试覆盖：图片结果局部展示、介绍独立提交、设施保存不携带介绍草稿、提交一个区域后保留另一区域草稿、审核中只禁用设施保存而不禁用选择、拒绝后恢复设施保存、结果未知重试恢复正确区域、5 秒只自动读取一次、下拉刷新结束动画。
- 运行小程序类型检查、一次生产构建和 Fixture 泄漏审计。
- 在真实 iPhone viewport 检查状态标签、按钮文字居中、底部安全区和三个区域的独立可操作性。
- 复用当前真实审核结果验证拒绝展示；不为 UI 调整额外触发 DashScope 调用。最终通过态继续在原定唯一一次真实场馆图片验收中验证。
