# 场地浏览切片：微信小程序原生设计预览规格

日期：2026-07-24

状态：待用户确认

上游规格：[足球场预订小程序：共享基础与场地浏览切片设计](./2026-07-22-pitch-booking-foundation-and-venue-browsing-design.md)

## 1. 目标与边界

本阶段只完成首个用户旅程的原生设计预览：

`场馆首页 → 查看可订时段 → 切换日期/场地类型 → 选择可订时段`

预览使用微信原生 `WXML + WXSS + TypeScript` 和隔离 Fixture，在微信开发者工具真实运行时展示。它既是设计 Artifact，也是后续正式前端的直接代码基础，不再从浏览器稿二次翻译。

本阶段不接后端、不登录、不创建订单、不支付，也不实现生产环境数据访问。Fixture 必须保留清晰的开发态边界，后续 HTTP 集成完成后按上游规格删除生产 Fixture 路径。

## 2. 已确认视觉方向

采用 A「可信运动感」：清爽蓝绿、内容优先、白色卡片和浅灰蓝页面背景。视觉目标是同时传达足球运动活力与价格、地址、时段库存的可信感。

浏览器方向稿只表达构图和气质。小程序真实运行结果是最终视觉真源；若两者存在渲染差异，以开发者工具中的原生页面为准，并反向更新设计 Token 和验收截图。

核心 Token：

- 主色：可信蓝 `#0284C7`；强调蓝 `#0EA5E9`。
- 可订：绿色 `#059669`，同时使用描边、底色和文字，不能只靠颜色表达。
- 页面背景 `#F8FAFC`；内容卡片 `#FFFFFF`；正文 `#10243E`；次要文字 `#64748B`；边框 `#DBE5EC`。
- 可订浅底 `#EFFBF6`；不可用文字 `#94A3B8`；暂时锁定提示色 `#B45309`。
- 系统字体，不下载网页字体。
- 字号层级为 `24/28/32/40rpx`，分别用于辅助信息、正文、区块标题和页面重点标题；主按钮为 `30rpx`。
- 圆角为 `16/24/32rpx`；间距为 `8/16/24/32/48rpx`。
- 所有主要点击目标至少约 `44 × 44px`，相邻点击目标至少约 `8px` 间隔。

## 3. 页面设计

### 3.1 场馆首页 `pages/venue/index`

从上到下：

1. 使用微信系统导航栏，标题“球场预订”；页面不自行绘制导航栏或胶囊避让区。
2. 场馆主图 Hero，底部渐变承载场馆名和一句卖点。
3. 标签行：五人制、七人制、夜场照明等真实设施标签。
4. 价格优势卡：突出“工作日白天低至 ¥360/小时”，但不把 Fixture 价格表达为最终承诺。
5. 信息区：地址、停车、营业时间、联系电话。本轮只做可读信息展示，不调用 `wx.openLocation` 或 `wx.makePhoneCall`；原生能力在正式前端状态补齐阶段实现。
6. 底部主按钮“查看可订时段”，进入时段页。

首轮原生预览展示 `ready` 和 `image-fallback`。`ready` 使用仓库内的开发态场馆示例图，避免网络和域名配置影响预览；使用开发者工具编译条件打开 `pages/venue/index?scenario=image-fallback` 时不渲染图片，改为固定蓝绿渐变、足球场线条装饰和“场馆图片待配置”文字。加载、错误、地图失败和拨号失败的完整状态在正式前端阶段继续补齐，不阻塞本次视觉方向验收。

### 3.2 可订时段页 `pages/availability/index`

从上到下：

1. 使用微信系统导航栏，标题“选择可订时段”。
2. 横向日期条，首屏至少可看到今天及后续三天；当前日期使用可信蓝实底。
3. 五人制/七人制分段选择器；选中项使用白色卡片和可信蓝文字。
4. 物理场地标题，例如“五人制 A 场”。
5. 两列时段网格，每格展示时间、价格或库存状态。
6. 状态说明，明确绿色描边代表可订。

时段至少覆盖：

- `AVAILABLE`：绿色描边、浅绿底、价格和“可订”文字；可点击。
- `SELECTED`：可信蓝实底、白字、“已选择”；再次点击取消。
- `EXPIRED`：中性灰、“已结束”；不可点击。
- `TEMPORARILY_LOCKED`：提示色文字、“暂时锁定”；不可点击。
- `BOOKED`：中性灰、“已预订”；不可点击。
- `CLOSED`：中性灰、“未开放”；不可点击。

页面始终单选。点击未选中的 `AVAILABLE` 会替换当前选择；再次点击同一时段会取消。切换日期或场地类型时清空选择。点击不可订时段不改变页面状态。本切片选择时段后不出现“预订成功”，只表达本地选择。

## 4. 原生预览结构与数据流

优先复用正式路由和正式组件边界：

- `venue-card`：包含 Hero、标签、价格优势和地址/停车/营业/电话信息，只接收场馆展示模型，不负责导航。
- `date-strip`：日期展示与选择事件。
- `pitch-filter`：场地类型切换事件。
- `slot-grid`：只按输入状态渲染时段并上报选择事件。
- 场馆页面：组合 `venue-card` 和底部主按钮，负责跳转。
- 时段页面：组合筛选器和 `slot-grid`，持有当前日期、场地类型和唯一的 `selectedSlotId`。

页面通过窄服务接口读取 Fixture。Fixture 只提供展示数据；组件不得直接导入 Fixture，避免后续接 API 时重写视觉组件。

本轮沿用现有 Fixture 字段和服务端语义，不另造展示契约：

| 模型 | 最小字段 |
| --- | --- |
| `VenuePreview` | `id`、`name`、`description`、`price_advantage_text`、`business_hours_text`、`address`、`parking_text`、`phone`、`images[]`、`facilities[]`、`pitch_types[]`、`availability_window` |
| `PitchType` | 稳定 `code`、`name`、`sort_order` |
| `PitchAvailability` | 稳定 `id`、`name`、`pitch_type`、`sort_order`、`slots[]` |
| `Slot` | 稳定 `id`、`starts_at`、`ends_at`、整数分单位 `price_cents`、`status` |

Fixture 状态枚举使用现有值 `AVAILABLE`、`EXPIRED`、`TEMPORARILY_LOCKED`、`BOOKED`、`CLOSED`。页面把 `EXPIRED` 显示为“已结束”，把 `TEMPORARILY_LOCKED` 显示为“暂时锁定”；`selectedSlotId` 是本地 UI 状态，不写回 Fixture。选择场地类型后，页面只展示 `pitch_type` 匹配的物理场地及其时段。

首轮只实现本地交互所需状态，不提前建设网络重试、权限、订单或支付基础设施。

## 5. 真实运行时对齐与验收

验收只看微信开发者工具中的原生渲染，不以浏览器截图作为像素基线。

首轮阶段性交付需要：

1. 两个页面能在微信开发者工具编译并打开。
2. 在 375px 和 390px 逻辑宽度下无页面级横向溢出；系统导航栏正常显示，页面内容不进入其区域。
3. 首页主按钮可进入时段页。
4. 日期、场地类型和可订时段可以点击；选中/取消与清空规则正确。
5. 各库存状态同时通过文字和视觉样式区分。
6. 关键颜色、字号、间距和圆角来自共享 Token，而不是页面散落的任意值。
7. `ready` 使用本地示例图稳定显示；`scenario=image-fallback` 稳定显示规定的渐变占位、线条装饰和提示文字。
8. 保存 375px 与 390px 的开发者工具截图，并额外保存一张 `image-fallback` 截图，作为本轮正式 Artifact；用户确认后才进入契约和后端阶段。

不同设备的系统字体、状态栏、安全区域和像素密度允许轻微差异；页面结构、信息层级、组件尺寸、状态语义和主要视觉比例必须一致。

## 6. 本轮明确不做

- 不接真实 API 或数据库。
- 不实现登录、微信授权、经营许可流程、订单和支付。
- 不为简单前端预览增加复杂安全审查、通用状态机或额外基础设施。
- 不同时展开其他业务模块。
