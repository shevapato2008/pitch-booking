## 1. 目标与用户旅程

本规格覆盖第二条用户旅程：

`选择可订时段 → 静默微信登录 → 主动授权手机号 → 填写联系人 → 确认价格与规则 → 创建待支付订单并锁定库存 → 查看订单详情`

本切片完成后，用户可以从已实现的可订时段进入单页确认页，使用微信身份和已验证手机号创建一个 `PENDING_PAYMENT` 订单。服务端在 PostgreSQL 事务中保存价格及联系人快照，并把目标时段锁定 10 分钟。

本切片不创建微信预支付单、不调用 `wx.requestPayment`、不处理支付通知或退款。支付能力属于下一条切片。

## 2. 临时交付规则

`modelstella.com` 的 ICP 备案、小程序微信认证、手机号能力和相关公网配置尚未完成。用户已明确批准：继续后续模块开发，只把每个模块依赖这些外部条件的最终交付步骤暂留。

因此本切片执行：

`设计 → 开发态 Fixture 前端 → 同尺寸视觉确认 → OpenAPI 契约 → 后端实现 → 本地前后端集成 → 自动化与开发工具验收`

暂留：

`公网 HTTPS → 微信合法域名 → 真实微信手机号授权 → 体验版真机 HTTP 验收 → 删除开发 Fixture → 最终交付证据`

暂留最终步骤不改变以下约束：

- 生产构建不能静默使用模拟微信身份或手机号；
- 生产环境缺少真实微信能力时必须明确失败；
- 模拟手机号不得混入正式业务数据；
- 本切片在最终步骤完成前标记为“开发完成、外部交付待办”，不声称正式交付。

## 3. 已选页面方案

用户已在 375×812 目标视口的三方案对比中选择 A“单页确认”。

页面由以下区域从上到下组成：

1. 订单标题与小程序导航安全区域；
2. 时段摘要卡：场馆、物理场地、日期、开始结束时间、时长和价格；
3. 联系人卡：微信手机号授权、脱敏号码、重新授权和联系人姓名；
4. 预订须知卡：10 分钟锁定、取消摘要和隐私用途；
5. 固定底栏：合计金额、禁用原因或“确认下单”按钮。

沿用已确认设计系统：背景 `#F8FAFC`、白色表面、正文 `#10243E`、次要文字 `#64748B`、边框 `#DBE5EC`、可信蓝 `#0284C7`、辅助蓝 `#0EA5E9`、可订绿 `#059669`；使用系统字体、现有圆角与间距令牌，触控目标不小于 88rpx。

不采用：

- 两步向导：多一次页面跳转，填写联系人时无法同时核对时段和价格；
- 底部面板：软键盘弹出后空间不足，规则、校验和异常状态容易拥挤。

## 4. 页面流程与权威边界

1. 用户只能从 `AVAILABLE` 时段进入确认页；路由只传 `slot_id`，不把前端展示价格作为权威输入。
2. 页面先执行静默业务登录；登录成功并取得业务令牌后，再读取受保护的结算快照。
3. 结算快照由服务端返回当前时段、价格、规则、可订状态、脱敏手机号和上次联系人姓名。
4. 用户主动点击微信手机号按钮。授权成功后，前端把一次性手机号凭证交给后端；前端只接收并展示脱敏号码。
5. 用户填写联系人姓名。填写阶段不锁库存。
6. 用户点击“确认下单”时，服务端重新锁定并检查时段、价格、身份和联系人。
7. 创建成功后跳转待支付订单详情，并使用服务端 `expires_at` 展示倒计时。
8. 同一用户对同一时段已有有效待支付订单时返回原订单。

权威边界：

- 服务端是库存、价格、订单状态、截止时间、微信身份和手机号验证结果的唯一权威；
- 小程序只提交 `slot_id`、非权威的 `checkout_version` 和联系人姓名，不提交权威金额或任意手机号；
- 微信临时凭证、手机号凭证和业务会话都不能作为日志字段；
- 本地倒计时只用于展示，不能自行修改订单或释放库存。

## 5. 页面状态与交互

### 5.1 初始与正常状态

- `LOADING_SESSION`：时段与价格使用骨架屏；联系人区不可提交；静默登录有独立超时及重试。
- `LOADING_CHECKOUT`：业务令牌已取得，读取受保护的结算快照；失败时只重试结算请求，不重复弹出授权。
- `READY_PHONE_REQUIRED`：结算数据和业务会话已就绪，显示“授权微信手机号”。
- `READY_CONTACT_REQUIRED`：手机号已验证并显示如 `138****5678`，联系人姓名为空或无效。
- `READY_SUBMITTABLE`：手机号和联系人有效，可创建订单。
- `SUBMITTING`：按钮加载且不可重复点击，页面离开前保留幂等键。
- `RESULT_RECONCILING`：请求结果未知，保留原请求体和幂等键，重放同一 `POST /orders` 直到取得首次结果；不得生成新键直接再次创建。

### 5.2 联系人校验

联系人姓名：

- 去除首尾空白后长度为 2–30 个字符；
- 允许中文、英文字母、数字、普通空格、间隔号 `·` 和连字符 `-`；
- 不允许纯空白；
- 在失焦或提交时就地显示稳定错误文案；
- 创建订单成功后保存为用户最近联系人，下次预填且允许修改。

不提供任意手机号文本输入。用户需要其他手机号时只能重新触发微信授权。

### 5.3 异常状态

- 静默登录失败：保留页面并显示重试，禁止创建订单。
- 手机号授权拒绝：不循环弹窗，解释履约用途并保留主动授权按钮。
- 当前账号无手机号能力：开发构建使用显式模拟场景；生产返回能力不可用且禁止提交。
- 价格变化：返回新结算快照，突出新旧价格并要求用户再次确认；不得自动按新价格创建。
- 时段不可售：显示“该时段刚刚被预订”，提供返回时段选择；不创建订单。
- 结果未知：使用同一幂等键和同一请求体重放创建请求，直到得到首次响应或明确错误。
- 订单创建成功：跳转订单详情；倒计时内显示“待支付”，不伪装已支付或已确认。
- 倒计时到零：订单详情立即显示“正在关闭支付”并禁用后续支付入口；使用订单详情接口触发安全过期检查，并每 2 秒短轮询，最长 30 秒。
- 过期完成：收到 `EXPIRED` 后停止轮询，显示“订单已过期”及“重新选择时段”入口；轮询超时或网络失败时保持“正在关闭支付”，提供显式重试，不把时段表达为已释放。

## 6. 小程序边界

新增页面与组件：

```text
miniprogram/
  pages/booking-confirmation/
  pages/order-detail/
  components/
    slot-summary-card/
    contact-card/
    booking-rules-card/
    order-submit-bar/
  services/
    auth/
    checkout/
    orders/
```

职责：

- `booking-confirmation` 组合登录、结算、手机号、表单和提交状态；
- `slot-summary-card` 只渲染服务端结算快照；
- `contact-card` 负责授权按钮、脱敏值、姓名输入和校验展示；
- `booking-rules-card` 显示锁定、取消及隐私用途；
- `order-submit-bar` 显示合计、禁用原因和提交进度；
- `order-detail` 展示订单编号、状态、时段、价格快照、联系人、场馆电话、导航和服务端倒计时。

现有 `Transport` 最小扩展为支持 `GET` 与 `POST`、headers、结构化 HTTP 错误和取消/超时。页面只能通过服务接口访问传输层。

微信原生能力收敛为两个窄接口：

```ts
interface WeChatIdentityCapability {
  login(): Promise<{ code: string }>;
}

interface WeChatPhoneCapability {
  // 真实实现由 open-type="getPhoneNumber" 用户事件提供一次性 code。
  normalizeEvent(event: unknown): { code: string };
}
```

开发场景实现只能被开发入口注册。生产入口绑定真实 `wx.login` 和真实手机号事件，不提供自动降级。

## 7. HTTP 契约

所有响应继续使用 `/api/v1`、`X-Request-Id` 和现有统一错误信封。受保护接口使用 `Authorization: Bearer <session_token>`。令牌不得出现在 URL。

### 7.1 创建业务会话

`POST /api/v1/auth/wechat/session`

请求：

```json
{"code":"一次性 wx.login code"}
```

响应：

```json
{
  "session_token":"opaque token",
  "expires_at":"2026-08-26T12:00:00+08:00",
  "user":{"id":"uuid","masked_phone":null,"last_contact_name":null}
}
```

后端以 `(wechat_app_id, openid)` 唯一定位用户；如微信返回 `unionid` 则单独保存，但本期不依赖它。微信 `session_key` 绝不返回客户端。

业务令牌为至少 256 bit 随机不透明值，数据库只保存安全哈希和到期时间。首版会话默认 30 天；重新登录可签发新令牌，过期令牌返回 `AUTH_REQUIRED`。

### 7.2 绑定微信手机号

`POST /api/v1/auth/wechat/phone`

请求：

```json
{"code":"一次性 getPhoneNumber code"}
```

响应：

```json
{"masked_phone":"138****5678","verified_at":"2026-07-27T12:00:00+08:00"}
```

后端使用真实微信 Provider 换取手机号并保存。响应、普通日志和错误详情不返回完整手机号。

### 7.3 读取结算快照

`GET /api/v1/slots/{slot_id}/checkout`

该接口必须携带业务会话，因为响应包含当前用户的脱敏手机号和上次联系人姓名。

响应至少包含：`slot_id`、场馆与物理场地摘要、日期、开始结束时间、时长、`price_cents`、币种 `CNY`、可订状态、取消规则摘要、锁定时长秒数、脱敏手机号、上次联系人姓名和整数 `checkout_version`。`checkout_version` 来自时段行的单调版本号；时段价格、时间或库存状态每次变化都递增。

该接口不创建订单，也不锁定原本可售的库存；它可以调用统一过期服务，安全回收无微信预支付单的过期锁。时段仍不可售时返回 `409 SLOT_NOT_AVAILABLE`，并允许客户端回到时段页刷新。

### 7.4 创建待支付订单

`POST /api/v1/orders`

请求头必须包含 `Idempotency-Key`。请求：

```json
{"slot_id":"uuid","checkout_version":12,"contact_name":"张三"}
```

响应使用 `201`；若同一用户、同一时段已有有效待支付订单，返回原订单和 `200`。响应至少包含：订单 ID、订单号、状态、价格快照、联系人姓名、脱敏手机号、创建时间、`expires_at` 和订单详情路径。

服务端在锁定时段行后比较 `checkout_version`。版本不一致且时段仍可售时返回 `409 PRICE_CHANGED`；标准错误信封的 `details.current_checkout` 包含完整新结算快照及新 `checkout_version`。前端用当前页面快照显示旧价格，用 `current_checkout` 显示新价格；用户确认后替换页面快照并使用新的幂等键提交新版本。若时段已不可售，返回 `SLOT_NOT_AVAILABLE`，不再返回价格变化。

幂等键作用域为 `(user_id, operation, idempotency_key)`，数据库建立唯一约束。订单、时段锁和最终幂等响应在同一事务提交：请求先插入幂等记录；并发同键请求在唯一约束处等待首事务，随后读取已提交结果。进程在提交前崩溃会整体回滚，不留下可见的 `PROCESSING` 记录。

相同键、相同摘要始终重放首次 HTTP 状态与响应，包括首次 `201`；相同键不同摘要返回 `409 IDEMPOTENCY_KEY_REUSED`。响应丢失时，客户端必须用同一键和同一请求体重放 `POST /orders`，不需要知道订单 ID，也不新增按幂等键查询接口。只有用户接受 `PRICE_CHANGED` 后请求体发生变化时，客户端才生成新键。

### 7.5 查询订单详情

`GET /api/v1/orders/{order_id}`

普通用户只能访问自己的订单。响应包含 PRD ORDER-04 要求的订单编号、状态、场馆、物理场地、时间、金额、联系人、导航资料、客服电话和取消规则。本切片可产生 `PENDING_PAYMENT` 和 `EXPIRED`；DTO 保留后续订单状态枚举的契约位置，但页面不伪造未实现状态。

当订单仍为 `PENDING_PAYMENT` 且 `expires_at <= now` 时，该接口先调用统一过期服务。因为本切片不会创建微信预支付单，安全条件满足时可在响应前原子变为 `EXPIRED`；条件未满足或处理暂时失败时返回当前状态，并通过 `closing_payment: true` 明确要求客户端继续显示“正在关闭支付”。

## 8. 数据模型与事务

本切片新增最小表或字段：

- `users`：微信主体标识、加密手机号、手机号验证时间、上次联系人姓名；
- `user_sessions`：令牌哈希、用户、签发和到期时间、撤销时间；
- `orders`：订单号、用户、时段、状态、价格快照、联系人姓名及加密手机号快照、创建与到期时间，以及 nullable `wechat_prepay_id`；本切片固定写 `NULL`，字段为下一支付切片的安全释放门禁；
- `idempotency_records`：用户、操作、键、请求摘要、最终 HTTP 状态和响应；对 `(user_id, operation, idempotency_key)` 建唯一约束；
- `slots`：补充 `locked_by_order_id`、`locked_until` 和 `checkout_version BIGINT NOT NULL DEFAULT 1`，使用现有状态字段表达 `AVAILABLE/LOCKED/BOOKED/CLOSED`；价格、时间或库存状态每次变更都原子递增版本；
- `slots.locked_by_order_id` 在本切片补为 nullable 外键，引用 `orders.id ON DELETE RESTRICT`。`LOCKED` 时订单外键与截止时间都必须非空，其他状态必须都为空；订单的 `slot_id` 继续引用时段，应用使用预生成 UUID 先插入订单、再设置锁定外键，避免循环外键插入歧义。

手机号属于敏感数据，统一由 `PhoneVault` 在应用层使用 AES-256-GCM 加密。每个值使用随机 96-bit nonce，并保存 `ciphertext_with_tag`、`nonce` 和 `key_version`；GCM 认证标签附加在密文末尾，AAD 固定包含记录类型、记录 UUID 和字段名，记录 UUID 由应用在加密前生成。当前 256-bit 密钥及版本只从部署 Secret 读取，生产环境缺失或长度错误时拒绝启动。开发环境使用独立开发密钥，禁止与正式数据共用。用户和订单模块只能通过 `PhoneVault.encrypt/decrypt/mask` 访问手机号，ORM、路由和普通日志不得直接处理明文。普通用户端订单详情始终返回脱敏号码；完整号码只为后续明确授权的履约管理员用例保留服务层解密能力，本切片不提供该接口。

创建订单必须在一个 PostgreSQL 事务内：

1. 校验会话、已验证手机号及联系人姓名；
2. 锁定目标 `slot` 行；
3. 查询同一用户、同一时段的有效 `PENDING_PAYMENT` 订单，有则返回原订单；
4. 若时段由一个已到期、仍为 `PENDING_PAYMENT` 且 `wechat_prepay_id IS NULL` 的订单锁定，调用统一过期服务原子过期原订单并释放仍属于它的锁；否则要求时段为 `AVAILABLE`；
5. 比较客户端 `checkout_version`；不一致则返回当前快照和 `PRICE_CHANGED`。一致时从锁定后的时段读取价格，创建订单价格和联系人快照；
6. 更新时段为 `LOCKED`，写入 `locked_by_order_id` 与服务端当前时间加 10 分钟；
7. 保存幂等结果并提交。

并发约束：同一时段最多关联一个有效锁定或已支付订单；更新时必须同时校验状态和 `locked_by_order_id`。至少 20 个并发请求争抢同一时段时，只能出现一个有效订单。

本切片新增 `PendingOrderExpiryService`，只处理 `wechat_prepay_id IS NULL` 的订单：始终先锁时段、再锁关联订单，重新检查订单仍为 `PENDING_PAYMENT`、`expires_at <= now`、时段仍为 `LOCKED` 且 `locked_by_order_id` 指向该订单，然后在同一事务把订单改为 `EXPIRED`，把时段改为 `AVAILABLE` 并清空锁字段。状态已变化时幂等返回当前结果。

该服务由三处调用：

1. availability、checkout 和订单详情查询在投影相关记录前，按需回收已到期且无预支付单的锁；
2. 创建订单在锁定目标时段后，按需回收该时段的安全过期锁；
3. 独立 expiry worker 每 30 秒无锁读取一批候选订单 ID，再逐个调用同一事务服务；候选读取不作为状态依据，服务内必须重查。单批默认 100 条，多实例允许重复扫描并依靠行锁和幂等状态迁移收敛。

因此查询、创建和 worker 共用同一业务规则，不能只依赖定时任务。下一支付切片必须把该服务升级为 PRD ORDER-03 的“先查单、再关单、最后释放”；一旦存在微信预支付单，本切片的快速释放分支永远不适用。

## 9. 微信 Provider 与开发模拟

后端定义：

- `WeChatIdentityProvider.exchange_login_code(code) -> {openid, unionid?, session_key}`；
- `WeChatPhoneProvider.exchange_phone_code(code) -> {country_code, national_number}`。

Provider 把微信响应解析为内部 DTO，并把无效/已使用凭证映射为 `WECHAT_LOGIN_FAILED` 或 `PHONE_AUTH_FAILED`，把账号能力或配置不可用映射为 `PHONE_AUTH_UNAVAILABLE`，把网络超时及微信 5xx 映射为可重试的同类 502 错误。路由与业务服务不得解析微信原始错误字符串。`session_key` 仅允许身份服务在当前登录交换中使用或按后续明确需求加密保存，本切片不持久化也不返回。

生产 Provider 使用 AppID/AppSecret 调用微信；凭证只从环境 Secret 读取。配置缺失、Provider 不可用或账号无手机号能力时返回稳定错误，不创建临时身份或手机号。

开发 Provider：

- 只在 `APP_ENV=development` 且显式启用开发场景时注册；
- 接受固定格式的非生产测试凭证，返回标记明确的测试身份和测试手机号；
- 开发数据与正式数据库隔离；
- `staging`、`production` 环境发现开发 Provider 配置时拒绝启动；
- 生产小程序包审计必须证明不含开发凭证、Fixture 响应或开发 Provider 绑定。

删除条件：微信认证完成、手机号能力可用、真实 AppID/AppSecret 联调通过、体验版真机授权成功且前后端真实 HTTPS 验收完成后，删除本切片运行路径中的开发 Fixture；开发测试工具可保留，但不得进入生产包。

## 10. 错误码

至少新增并测试：

| 错误码 | HTTP | 含义 |
| --- | ---: | --- |
| `AUTH_REQUIRED` | 401 | 会话缺失、无效或过期 |
| `WECHAT_LOGIN_FAILED` | 502 | 微信登录凭证交换失败 |
| `PHONE_AUTH_REQUIRED` | 422 | 用户尚无已验证手机号 |
| `PHONE_AUTH_UNAVAILABLE` | 503 | 当前微信账号或 Provider 无手机号能力 |
| `PHONE_AUTH_FAILED` | 502 | 手机号凭证无效或微信交换失败 |
| `INVALID_CONTACT` | 422 | 联系人姓名无效 |
| `SLOT_NOT_AVAILABLE` | 409 | 时段已锁定、已订或关闭 |
| `PRICE_CHANGED` | 409 | 用户所见结算版本已变化，需重新确认 |
| `IDEMPOTENCY_KEY_REUSED` | 409 | 相同幂等键用于不同请求 |
| `ORDER_NOT_FOUND` | 404 | 订单不存在或用户无权访问 |

`checkout_version` 只是乐观并发版本，不承担鉴权或防篡改；服务端仍从锁定后的时段读取金额。猜测版本不能改变价格，只会得到当前权威结果或版本冲突。
