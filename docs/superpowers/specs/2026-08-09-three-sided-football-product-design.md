# 天津足球场预订小程序：三类用户与开放球局产品设计

**日期：** 2026-08-09

**状态：** 产品方向已确认；2026-08-09 根据可扩展地图目录合并结果完成最小修订

**范围：** 产品方向、核心旅程、关键页面和首期边界；不包含实现计划

**视觉稿：** `artifacts/ui/concepts/open-game-marketplace/review-board.html`

## 1. 结论

产品不应拆成“球场端、球队端、散客端”三个互不相通的系统，而应成为：

> 以真实场地交易为底座，连接球场、组织者和球员的可信足球活动平台。

一名微信用户可以在不同场景中同时拥有不同角色：今天是散客，下周是队长，也可能是某家球场的工作人员。账号保持统一，权限跟随场馆、球队或球局关系授予。

三类需求通过一条真实链路连接：

```text
球场开放真实库存
→ 球队完成订场
→ 队长把缺少的名额公开
→ 散客申请并到场
→ 可靠球员成为球队常客
→ 球队更容易成局，球场获得更多复购
```

首期不建设泛社交平台。社交关系从真实报名和真实到场中产生，而不是先建设动态、私聊、排行榜或推荐算法。

## 2. 当前项目基线

现有项目已经本地闭环：

- 可扩展的天津场馆地图目录前端形态，包括城市/用户定位/POI 搜索中心、区域和“仅看可订”筛选、标记聚合及纵向场馆列表；
- 一家 `ONLINE` 合作场馆及四家 `DIRECTORY_ONLY` 场馆；
- 在线场馆详情、未来 14 天时段和价格；
- 登录、手机号授权、订单锁场、订单过期；
- 服务端权威支付确认与订单详情；
- `Venue → Pitch → Slot → Order → Payment` 数据和事务边界。

尚未实现：

- 场馆管理员身份和工作台；
- 球队、球局、公开名额、报名、候补和到场记录；
- 我的订单/我的报名；
- 退款、核销和完成状态；
- 生产可用的 POI 搜索适配器及由真实场馆目录返回的区域元数据；当前百条场馆和区域 sidecar 仍属于隔离预览 Fixture；
- 真实微信生产支付及公网部署。

因此，开放球局应作为现有订单之上的新层，不重写已经稳定的订场和支付基础。地图的新前端形态先按“切片 0”收口，不能把预览数据量误认为已经具备多场馆真实供给。

## 3. 已确认的首期边界

1. 采用“真实订场＋开放名额”路线。
2. 队长发布的公开球局必须绑定本人已支付确认的订单。
3. 首个开放球局切片只允许已支付队长发布；经过审核的场馆发布官方球局属于后续能力，仍须先建立权威锁场记录。
4. 散客首期只在平台报名占位；预计费用透明展示，但在线下结算。
5. 只在唯一具备在线库存的合作场馆灰度，不向四家目录场馆开放报名承诺。
6. 陌生人公开球局首期仅限 18 周岁以上用户。
7. 统一用户身份，不要求注册时永久选择“队长”或“散客”。
8. 小程序顶层信息架构为“找球场｜找球局｜我的”；具体底部导航需单独完成视觉确认，不能直接覆盖现有全屏地图和底部抽屉。

## 4. 核心数据边界

场地库存和球局名额是两件事：

- `Slot` 回答“这块场地还能不能被预订”；
- 球局容量回答“这场已经订好的活动还能不能加入”。

一个时段显示“已订”，可能恰好意味着该球队正在开放散客名额。因此“找球场”和“找球局”保持独立入口，但共享场馆、订单和导航信息。

首期关系如下：

```text
Venue
  └─ Pitch
      └─ Slot
          └─ Confirmed Order
              └─ Game
                  └─ Registration
```

必要的新对象只有：

- `Team`：最小球队资料和队长归属；
- `Game`：绑定已确认订单的活动及公开名额；
- `Registration`：散客申请、加入、候补、退出和到场结果；
- `VenueMembership`：球场工作人员与场馆权限关系；
- 操作记录：保存关键发布、审批、移除、取消和到场动作。

一个已确认订单同一时刻最多绑定一个未取消球局，避免同一块已订场地被重复包装成多个公开供给。

首期不新增散客支付、钱包、平台分账、聊天消息或复杂信用分。

## 5. 三类用户旅程

### 5.1 球场方

首期由平台审核并配置场馆管理员，不允许商家提交后自动获得权限。后续独立切片允许场地方提交认领或加盟申请，但仍须平台独立核验和批准。

核心旅程：

```text
进入场馆工作台
→ 查看今日订单和场地状态
→ 批量开放未来时段并设置价格
→ 必要时修改未售价格或临时关闭
→ 用户端立即看到真实状态
→ 当天确认到场和完成
```

最小功能：

- 管理物理场地、时段、价格和关闭状态；
- 查看今日订单及履约联系人；
- 确认整场订单到场和完成。

场馆内容仍由平台协助维护，完整资料编辑和经营报表不阻塞首期工作台。

场馆官方散客局放到后续阶段。届时也必须先为活动建立权威锁场记录，不能发布没有真实场地保障的活动。

### 5.2 球队与队长

核心旅程：

```text
找球场并支付订单
→ 在预订成功页选择“创建球局”
→ 填写球队、总人数和已有固定人数
→ 设置开放名额、水平、位置需求和预计 AA
→ 公开发布或只分享链接
→ 审核散客、处理退出和候补
→ 赛后记录到场
```

创建球局需要的信息：

- 球局名称和球队名称；
- 总人数、已有固定人数和开放名额；
- 对抗强度与最低经验说明；
- 是否需要门将或其他位置；
- 预计人均费用，并明确“线下结算、平台不代收”；
- 报名截止时间；
- 装备和到场说明；
- `PUBLIC` 或 `LINK_ONLY` 可见范围；两种范围都使用相同的申请审核规则。

订单中的场馆、场地和时间自动带入且不可修改。已有散客加入后，预计费用只能降低不能提高；容量不能降到已加入人数以下。

### 5.3 散客

核心旅程：

```text
浏览公开球局
→ 查看真实场地、时间、人数、水平和费用
→ 登录
→ 确认已满 18 周岁及运动风险提示
→ 提交加入申请
→ 队长接受、候补或婉拒
→ 开场前收到状态提醒
→ 到场踢球
→ 形成到场记录，后续可再次参加
```

游客可以浏览公开球局，但申请时才需要登录和成年确认。首期不为公开报名额外收集手机号或身份证。队长只看到微信展示身份、足球位置、报名备注和必要的历史到场摘要。

## 6. 找球局的信息架构

### 6.1 球局列表

首期只有一家场馆，无需建设复杂地图和推荐算法。默认按开场时间排序，提供三个轻量筛选：

- 日期；
- 五人制/七人制；
- 仅看仍有名额。

首期不把“找球场”已经具备的 POI 搜索、区域筛选和标记聚合复制到“找球局”。这些能力只在未来开放多个真实在线场馆后复用。

每张球局卡片必须显示：

- 场地已确认；
- 日期、时间和场地规格；
- 当前人数和剩余名额；
- 对抗强度或新手友好程度；
- 预计 AA 金额及线下结算；
- 队长/场馆组织者身份；
- 报名截止时间。

### 6.2 球局详情

信息顺序为：

1. 场地真实性与时间；
2. 当前人数和剩余名额；
3. 水平、位置和装备要求；
4. 预计费用及结算边界；
5. 组织者履约摘要；
6. 退出、风险和隐私规则；
7. “申请加入”主操作。

公开页面不展示完整成员名单、手机号、微信号或队内备注。

### 6.3 我的

“我的”聚合：

- 我的订单；
- 我的报名；
- 我组织的球局；
- 我的球队；
- 具备权限时显示“场馆工作台”。

## 7. 最小状态与规则

### 7.1 球局状态

只保留五个业务状态：

- `DRAFT`：尚未公开；
- `PUBLISHED`：已经公开；
- `SUSPENDED`：订单退款或场地状态暂不确定，暂停新报名；
- `CANCELLED`：活动取消；
- `COMPLETED`：活动结束并完成到场记录。

“招募中、已满、报名截止、进行中、已结束”根据人数和时间计算，不再增加独立数据库状态。订单进入退款申请或场地不确定状态时先暂停招募，已有报名保留但不能新增或递补；退款被驳回/撤回且订单仍为 `CONFIRMED` 时恢复为 `PUBLISHED`；退款成功或场馆取消时取消球局及其报名。仅取消球局不会自动取消对应订场订单。

### 7.2 报名状态

- `APPLIED`：等待队长审核；
- `JOINED`：已加入并占用公开名额；
- `WAITLISTED`：当前满员，等待空位；
- `REJECTED`：组织者婉拒；
- `WITHDRAWN`：用户退出；
- `REMOVED`：组织者移除；
- `CANCELLED`：随球局取消；
- `PRESENT` / `NO_SHOW` / `UNMARKED`：独立的赛后到场结果。

申请、接受、退出和候补递补必须以服务端容量为准，避免最后一个名额被多人同时占用。公开和私域链接球局都先由队长审核；满员后进入候补，正式成员退出时按候补顺序自动转正。

### 7.3 简单时间规则

- 默认开场前 2 小时停止新申请；
- 开场前至少 6 小时退出，不记录“临时退出”；
- 6 小时内退出会被记录，但首期不做自动封禁或扣款；
- 未退出且未到场记为 `NO_SHOW`；
- 球局取消时所有报名统一取消，不影响球员记录。

这些规则首期固定，避免每位队长配置不同规则。

## 8. 信任、安全与隐私

只建设支撑陌生人到场的最小能力：

- 公开球局必须有真实订单；
- 申请人必须完成微信身份会话和成年人确认；
- 不收集身份证照片或无必要的紧急联系人；
- 不开放陌生人私聊和自由文本公开评论；
- 提供结构化举报：虚假信息、临时加价、危险行为、骚扰和未到场；
- 严重事件由平台人工处理，首期不建设自动信用算法。

首期只记录简单到场事实，不展示星级或综合信用分，也不据此自动封禁。人工举报和平台下架足以支撑单场馆灰度。

申请结果、候补转正、球局取消和开场提醒直接影响陌生人能否正常到场，因此对应的微信订阅消息属于 MVP 必需能力；消息发送失败不能改变报名或球局的服务端状态。

运动风险提示不能替代球场和活动组织者应履行的安全保障义务。公开球局上线前应由专业人员复核协议、保险和现场责任安排。

## 9. 冷启动与验证

首期不追求全天津覆盖，只在合作场馆形成可重复的小密度市场：

1. 邀请 5—10 名已有真实订单的合作队长；
2. 鼓励他们只开放确实缺少的 1—4 个名额；
3. 通过微信群分享卡片，同时在“找球局”页展示；
4. 平台人工跟进首次申请、取消和到场；
5. 每周复盘哪个时间、规格和球队更容易补满。

北极星指标不是注册数或申请数，而是：

> 每周通过公开球局成功到场的散客席位数。

建议用 8 周判断是否继续投入。原订场业务指标继续有效：至少 30 名有效队长、50 笔付费订单、15 名复购队长、非黄金时段利用率超过 20%，且超卖和账实差异均为 0。新增开放球局指标：

- 至少 20 场公开球局、8 名独立组织者和 30 名独立申请者；
- 发布满 24 小时的球局中，至少 60% 获得真实申请；
- 公开名额平均填补率不低于 50%；
- 已加入散客到场率不低于 85%；
- 组织者临时取消率不高于 5%；
- 没有严重安全或隐私事故。

这些是产品验证阈值，不是对外承诺。若供给不足，先增加合作队长和固定周场，不通过开发推荐算法解决。

## 10. 轻量分期

遵循单旅程闭环，限制并行在制品：

### 切片 0：收口可扩展地图目录

先在既定目标视口完成当前地图参考图、实现图、并排图和叠加/差异图的用户确认。视觉确认后再冻结区域字段和 POI 能力边界，接入真实目录元数据与生产 POI 适配器，并删除百条场馆及区域 sidecar Fixture。这里只收口已合并的地图旅程，不增加新地图功能。

### 切片 1：场馆真实运营

合作场馆管理员能够维护未来时段、价格和关闭状态，并查看今日订单。解决当前生产库存仍依赖平台人工的问题。

### 切片 2：补齐订单履约

完成我的订单、取消退款、到场和完成状态，为球局取消联动和真实履约提供基础。

### 切片 3：队长开放名额

已支付队长从订单创建球局，生成公开详情和分享卡片。此时可以先用隔离 Fixture 完成视觉确认，再接真实订单契约。

### 切片 4：散客申请与队长审核

开始该切片的 Artifact 前，先把三入口导航作为当前旅程所需的最小共享基础完成视觉确认；此前保持现有页面路由，不提前把底栏叠加到地图。随后完成找球局、申请、接受、候补、订阅通知和我的报名，形成第一条真实陌生人到场旅程。

### 切片 5：退出、到场与治理

增加退出、取消联动、队长记录散客到场/爽约、举报和人工纠错。场馆管理员只确认整场订单是否到场，不评价单个散客。

### 切片 A3：场馆加盟、认领与平台管理后台

在三目的生产入口和“我的场馆”组合页稳定后，立即建设场馆加盟、认领及独立 Web 审核后台，不把平台权限入口暴露在普通小程序中。小程序“我要出租场地”始终先进入“我的场馆”：统一展示零个、一个或多个已授权场馆，并始终提供“认领已有场馆”和“创建新场馆”两个独立入口；平台工作人员核验申请、批准或拒绝，并保留操作者、时间、结果和原因。队长开放名额、找球局和治理切片在该闭环之后继续。

未核验的新场馆先写入独立的加盟申请，不进入公开 `venues`。批准时在同一事务中创建正式场馆和首位管理员 `venue_memberships`；新场馆保持 `is_listed=false`，完成资料、物理场地和库存配置并通过内容审核后再公开。平台主动招商时先创建一次性、短期有效的邀请，场地方微信登录接受邀请并补充资料，但接受邀请本身不等于获得权限。

认领已有场馆时，申请必须绑定现有 `venue_id`；批准只创建或激活该场馆与申请用户之间的 `venue_memberships`，不得再创建或复制 `venues`。新场馆加盟只有在去重和核验通过后才执行上述新建事务。

后台 API 必须校验平台级角色，例如 `PLATFORM_ADMIN` 或 `ONBOARDING_REVIEWER`。普通用户、场馆管理员和知道后台地址的人均不能据此前端入口获得平台权限。该切片只做加盟/认领审核与授权，不扩展经营报表、客服工单或综合运营平台。

复制球局、常客关系、场馆官方球局和平台内散客支付放在真实到场指标通过以后。

## 11. 明确不做

- 商家提交后自动创建公开场馆或自动获得管理权限；
- 全天津公共社交广场；
- 私聊、群聊、动态和公开评论；
- 球员星级、水平算法和智能匹配；
- 散客在线 AA、钱包、分账和队长提现；
- 未成年人公开拼场；
- 联赛、战绩、积分榜和复杂球队主页；
- 多运动品类；
- 为四家目录场馆伪造库存或球局。

## 12. 设计验收边界

本文件和概念稿只确认产品方向，不代表视觉或实现已经通过。当前可扩展地图目录仍须先完成切片 0 的同视口视觉确认与真实能力接入。进入后续每个切片时继续按当前项目方法，在目标视口制作真实运行时 Demo，完成同尺寸参考图、实现图、并排图和叠加/差异图，经用户确认后再冻结契约和开发后端。
