# 目的入口与场馆单日库存切片设计

**日期：** 2026-08-10

**状态：** 共享入口视觉已确认；场馆库存交互方案已确认，待独立 Artifact、Fixture Demo 和同 viewport 对比确认

**前序决策：** [三类用户与开放球局产品设计](./2026-08-09-three-sided-football-product-design.md)

## 1. 结论

小程序不要求用户注册时永久选择“球场方、队长或散客”。首次进入时先用三个同等权重的目的入口分流：

1. **我要出租场地**：申请合作，或进入已有权限的场馆工作台；
2. **我要租赁场地**：为球队寻找并预订整块场地；
3. **我要找球踢**：目标能力是让没有球队的用户浏览并申请加入已经锁定真实场地的开放球局；该能力当前尚未实现。

用户以后再次打开小程序时进入综合首页。综合首页继续保留三个平权入口，同时展示最近一次任务和“我的”入口。用户选择的是当下目的，不是永久身份。

散客入口使用日常语言“我要找球踢”。进入该模块后，页面标题和领域对象再使用“找球局”“球局详情”和“申请加入”。

## 2. 为什么采用三个平权入口

采用用户确认的“三入口平权”方案，原因是：

- 首屏直接回答用户“我来这里要做什么”，比展示内部模块名称更容易理解；
- 同一个微信用户可以在不同时间拥有不同目的，不需要切换账号或角色；
- 三种目的都保持稳定位置，便于形成记忆；
- 副标题承担权限和业务边界说明，不让“出租场地”被误解为任何人都能立即发布。

未采用“踢球者优先、场馆方次级入口”，因为用户明确希望首屏像房产平台一样让不同目的并列。未采用纯频道切换器，因为它更像功能分类，弱化了首次进入时的意图引导。

## 3. 首次进入与回访首页

### 3.1 首次进入

目标视觉对比 viewport 为 `375 × 812`。页面使用自定义头部；头部不能依赖固定 `rpx` 或 `env(safe-area-inset-top)` 猜测安全区，必须在运行时根据 `wx.getWindowInfo().statusBarHeight` 和 `wx.getMenuButtonBoundingClientRect()` 计算标题行的顶部、高度和右侧胶囊避让。页面只包含：

- 左上角当前城市入口“天津⌄”；
- 标题“你今天想做什么？”；
- 一句说明“选择一个目的开始，之后可以随时切换”；
- 三张相同尺寸、相同层级的目的卡片；
- 说明“这里选择的是当下目的，不是永久身份”。

当前只有天津具备真实供给，因此首期必须有城市入口，但不增加独立的首次城市选择页，也不在进入页面时强制申请定位权限。点击“天津⌄”打开轻量城市选择层：

- “天津”显示为当前且已开放；
- 其他城市统一显示“敬请期待”，不伪造可订场地；
- 关闭后仍停留在当前目的入口页，不丢失用户上下文。

这只是开发态视觉 Fixture 和交互，不引入城市后台、城市 API、多城市库存查询或开城意向收集。等至少两个城市有真实供给时，再单独设计首次城市选择和定位策略。

三张卡片的正式文案为：

| 入口 | 副标题 | 目标去向 | 当前状态 |
| --- | --- | --- | --- |
| 我要出租场地 | 申请合作，或进入已授权的场馆工作台 | 权限判断后进入工作台或合作接入说明 | 本切片实现工作台灰度旅程；综合首页暂不发布 |
| 我要租赁场地 | 为球队查找时间、价格和可订整场 | 现有地图找场、时段、下单和支付旅程 | 已有真实闭环 |
| 我要找球踢 | 没有球队，也能加入已锁定场地的开放球局 | 找球局列表、详情、申请、审核或候补旅程 | 当前未实现，只进入 Artifact/Fixture，不进入生产包 |

浏览球场不要求先登录；找球局实现后也遵循游客可浏览、申请时登录的边界。进入场馆工作台或提交订单时，在动作边界完成身份验证。

### 3.2 回访首页

回访首页不是再次强制选择的门槛。它包含：

- 与首次进入一致的左上角“天津⌄”城市入口和动态安全区；
- 顶部“我的”入口；
- 三个同等尺寸的快捷入口：出租场地、租赁场地、找球踢；
- “继续上次”区域，只恢复最近浏览或操作的模块，不自动执行写操作；
- “我的进行中”摘要，只显示真实订单、报名或场馆待办。

没有进行中事项时直接省略该区域，不用模拟数据填充首页。首期不建设推荐流、社交动态、广告位或经营报表。

本地只保存最近使用的目的和可公开恢复的页面位置。订单、报名、场馆权限和待办数量必须来自服务端权威数据。

## 4. 下一条垂直切片

共享入口的 Artifact、Fixture 和同 viewport 视觉证据已经完成并获得用户确认。当前唯一在制品是下面的场馆库存旅程：

```text
已获授权的场馆工作人员
→ 打开平台定向提供的场馆工作台小程序路径
→ 完成登录和场馆权限校验
→ 场馆工作台
→ 选择日期和物理场地
→ 新增一个未来时段，或选择一个尚未售出的已有时段
→ 新增时设置起止时间与价格；编辑时修改开放状态或价格
→ 确认保存
→ 用户端读取到更新后的真实库存
```

该切片只服务唯一 `ONLINE` 合作场馆“渤海元丰足球场”，不为四家 `DIRECTORY_ONLY` 场馆创建库存或管理员权限。

首次目的选择和回访综合首页已经作为前置完成 Artifact、隔离 Fixture 与视觉确认，不属于当前库存切片。由于“找球踢”当前没有真实闭环，生产首页暂不启用三入口。灰度场馆工作人员通过平台定向提供的小程序页面路径或二维码进入工作台；该入口仍执行同一登录与 membership 校验，猜测页面路径不能获得权限。等三个目的都有真实、状态诚实的去向后，再独立启用综合首页。

### 4.1 最小工作台页面

工作台默认打开今天的库存视图，页面只包含：

- 场馆名称；
- 一周七天的横向日期条，以及调用小程序日期选择器的“更多日期”；
- 五人制/七人制物理场地切换；
- “新增时段”操作；
- 当日时段列表；
- 每个时段的开始结束时间、价格和状态；
- 新增时段的开始时间、结束时间和价格底部面板；
- 未售已有时段的“调整价格”和“临时关闭/重新开放”底部面板；
- 保存中的反馈、成功反馈和可恢复错误。

日期条只负责选择一天，时段列表只展示该日所选物理场地的真实库存。首期不采用 Google Calendar 式周时间网格，也不支持拖拽创建或拖拽调整；手机端完整周网格会压缩状态、价格和触控区，并与页面纵向滚动产生手势冲突。

“新增时段”以场馆当地时间按 30 分钟递增选择开始和结束时间，因此可以创建 `09:30–11:00`。新时段保存成功后状态为 `AVAILABLE`。已有时段的起止时间保持只读；首期只允许修改价格或开放状态，不把“调整时间”伪装成可用能力。

首切片不包含批量开放、周期模板、批量复制、拖拽排程、修改已有时段起止时间、删除时段、场馆资料编辑、经营报表、官方球局或今日订单履约。这些属于后续独立旅程。

### 4.2 新增与修改边界

新增时段必须同时满足：

- 用户具有所选场馆的有效库存管理权限；
- 所选物理场地属于该场馆；
- 起止时间位于同一个场馆当地日期，均对齐到 30 分钟边界，开始早于结束且尚未开始；
- 价格与现有库存一致，使用非负整数分保存，界面使用人民币元显示；新增和修改都在服务端验证该约束；
- 时间范围统一为半开区间 `[starts_at, ends_at)`，相邻时段合法；与同一物理场地任何已有时段均不重叠，包括 `AVAILABLE`、`CLOSED`、`LOCKED` 和 `BOOKED`；
- 服务端在受保护事务中重新检查权限、归属、时间、价格和重叠条件，并复用数据库既有 `ex_slots_no_overlap` 排斥约束作为并发写入的最终保障，才创建 `AVAILABLE` 时段并返回服务端生成的 ID 与初始 `checkout_version`。

若创建请求与最新库存冲突，客户端保留用户输入，显示“与已有时段冲突，请调整时间”，并刷新当天权威库存；不能先显示成功再异步回滚。首期不允许删除或修改已创建时段的起止时间，误建时段只能先临时关闭并联系平台处理，不能在客户端绕过重叠规则创建替代时段。

只有 `AVAILABLE` 或 `CLOSED` 且没有有效订单占用的未来时段可以修改：

- `AVAILABLE`：可以修改价格或临时关闭；
- `CLOSED`：可以修改价格并重新开放；
- `LOCKED`：展示“用户下单中”，不可修改；
- `BOOKED`：展示“已售出”，不可修改；
- 已经开始的时段：只读。

“没有有效订单占用”不由管理员接口另建一套订单判断，而由持久时段状态表达。管理员读取复用现有安全过期/支付收敛服务：只有权威确认可释放的锁才能转回 `AVAILABLE`；`LOCKED` 即使本地截止时间已过，或关联订单处于 `PAYMENT_EXCEPTION`/支付结果未知，也继续只读。`BOOKED` 始终只读。管理员写入不得自行释放锁或改变订单、支付状态。

已有时段的起止时间始终只读。管理员契约直接把现有 `checkout_version` 暴露为并发版本；价格或开放状态变化都递增它，使旧结账快照和旧管理员编辑同时失效。保存时客户端提交用户明确修改的目标值和 `expected_checkout_version`，不根据旧页面状态自行推断成功。

服务端在同一事务和受保护写入中重新校验：有效库存管理权限、场馆与物理场地归属、未来时段、非负整数分价格、持久状态为 `AVAILABLE`/`CLOSED`，以及当前 `checkout_version` 等于 `expected_checkout_version`。成功时原子更新价格/状态并递增 `checkout_version`。状态或版本不匹配时返回当前权威时段；客户端显示“该时段状态已变化”并刷新，不静默覆盖其他管理员或订单流程的修改。

### 4.3 前端单元与数据流

首切片保持三个可独立理解的前端边界：

- 库存工作台页面：持有当前日期、物理场地和加载状态，只请求并展示所选单日库存；
- 时段编辑面板：使用 `CREATE` 或 `EDIT` 两种显式模式。`CREATE` 编辑起止时间和价格，`EDIT` 只编辑价格与开放状态；
- 库存服务端口：向页面提供读取单日库存、新增单个时段、更新单个时段三个操作。开发态 Fixture 和生产 HTTP 适配器实现同一端口，但生产构建只能注册 HTTP 适配器。

读取流程为“选择日期/场地 → 请求权威单日库存 → 按开始时间排序展示”。管理窗口与现有用户端可订窗口保持一致，只允许今天至今天后第 13 天，共 14 个自然日；“更多日期”也只能选择该窗口，避免管理员创建用户端暂时不可见的库存。

快速切换日期或场地时，页面为每次读取生成递增请求序号；只有与当前日期、场地和最新序号一致的响应可以更新页面，迟到响应必须丢弃。

写入流程为“打开面板 → 本地完成必要格式检查 → 生成并持久保存本次 `Idempotency-Key` → 提交明确目标值 → 等待服务端权威结果 → 成功后用返回时段替换或加入列表”。新增和修改复用现有 `idempotency_records`，分别使用固定 operation `CREATE_ADMIN_SLOT` 与 `UPDATE_ADMIN_SLOT`；同一用户、operation、key 和相同请求重放已提交的响应，同 key 不同请求返回 `IDEMPOTENCY_KEY_REUSED`。服务端把库存写入和幂等完成记录放在同一事务，避免留下“时段已改但幂等记录未完成”的中间状态。

若请求超时或连接中断，客户端保持面板和输入，标记“正在确认保存结果”，使用原 `Idempotency-Key` 重试；不可生成新 key，也不可宣称失败或成功。得到重放结果后再关闭面板并刷新单日库存。客户端不自行合并 `checkout_version`，也不根据旧列表推断写入成功。

## 5. 权限与权威边界

场馆方入口平权，不代表发布权限平权。

- `VenueMembership` 是场馆权限的服务端权威；首期只把平台创建且批准的库存管理员写入该关系，不建设普通场馆成员体系；
- 一条 membership 只有在 `can_manage_inventory=true` 且未被撤销时，才允许读取或修改工作台库存；
- 首期管理员由平台审核配置，不开放商家自助注册；
- 无场馆权限的用户进入合作接入说明，不能看到联系人、订单或库存编辑能力；
- 有效库存管理员只能操作 membership 绑定的 `venue_id`；客户端传入其他场馆 ID 不能扩大权限；
- 服务端在每次库存写入的受保护事务内重新检查 membership、能力和撤销状态，不能只依赖登录时或页面加载时的判断；
- 权限失效时，正在打开的编辑页必须在保存时得到明确拒绝并刷新为只读状态。

场馆内容资料仍由平台协助维护。该切片不增加名称、地址、图片、电话等 CMS 编辑权限。

## 6. 前端状态与失败处理

共享入口视觉基础已经覆盖并确认三个 `375 × 812` 状态：

1. 首次目的选择；
2. 首次目的选择的城市选择层打开；
3. 回访综合首页。

这三个状态已经冻结，不继续进入契约或后端，也不启用生产首页。当前库存工作台切片使用独立的 Artifact 和 Fixture，至少覆盖：

1. 单日库存就绪及可编辑时段；
2. 新增 `09:30–11:00` 时段的底部面板；
3. 已有时段编辑面板及保存中/保存失败反馈。

必要状态语义：

- 页面加载失败：保留页面结构，提供“重新加载”；
- 保存中：当前编辑操作不可重复提交，其他页面不伪造成功；
- 写入结果未知：保留面板与输入，显示“正在确认保存结果”，使用原幂等键重试；
- 新增重叠：保留起止时间和价格输入，显示冲突并刷新当天库存；
- 并发变化：显示“该时段状态已变化”，刷新权威状态；
- 权限不足：退出编辑态，说明需联系平台管理员；
- 无当日时段：显示真实空状态和“新增时段”，不自动生成 Fixture 到生产包。

错误必须按权威边界区分，不统一伪装成冲突：

| 类别 | HTTP / 错误码 | 前端行为 |
| --- | --- | --- |
| 未登录或会话失效 | `401 AUTH_REQUIRED` | 重新登录；不展示库存写入结果 |
| 无场馆库存权限 | `403 INVENTORY_PERMISSION_REQUIRED` | 退出编辑态；不在错误详情中返回库存 |
| 日期、时间、价格或字段非法 | `422 INVALID_ARGUMENT` | 保留输入并在对应字段说明 |
| 新增与已有时段重叠 | `409 SLOT_OVERLAP` | 保留输入，刷新授权范围内的单日库存 |
| 已有时段状态或版本变化 | `409 SLOT_STATE_CHANGED` | 关闭编辑态并用响应中的当前时段刷新 |
| 幂等键被不同请求复用 | `409 IDEMPOTENCY_KEY_REUSED` | 停止自动重试并重新生成一次用户操作 |
| 服务不可用或结果未知 | 网络错误或 `503 SERVICE_UNAVAILABLE` | 不宣称失败；按原幂等键确认结果 |

两组 Fixture 都只存在于开发组合根，不同时推进。共享入口 Fixture 在视觉冻结后停止变化，并在未来生产综合首页开始集成前删除；库存 Fixture 在库存契约和后端集成完成后删除。生产构建不得包含场馆权限、库存或保存成功的模拟业务数据。

## 7. 视觉规则

沿用现有小程序设计系统，而不是采用新的营销型主题：

- 背景 `#F8FAFC`，表面 `#FFFFFF`，主文本 `#10243E`；
- 信任蓝 `#0284C7`，可用绿 `#059669`，锁定/注意状态使用既有语义；
- 系统字体、现有 `rpx` 字号和 8rpx 间距体系；
- 触控区域至少 `88rpx`；
- 使用统一 SVG/原生图标，不使用 emoji 充当功能图标；
- 三个目的入口的尺寸、字重和交互反馈相同；
- 库存工作台使用单列布局；一周日期条、物理场地标签和时段列表构成由上至下的稳定层级；
- 新增与编辑均使用底部轻量面板；新增面板明确显示日期、物理场地、时长与“新增并开放”，编辑面板明确显示起止时间只读；
- 头部城市文案必须完全位于状态栏下方、微信胶囊左侧；在 iPhone X `375 × 812` 完成主视觉对比，并在 iPhone 14 Pro 做一次不增加 Artifact 的安全区烟雾检查；
- 城市选择层使用底部轻量面板；“天津（已开放）”与“其他城市（敬请期待）”必须同时使用文字表达状态；
- 状态不能只靠颜色表达，必须同时显示文字。

视觉验收在相同目标 viewport 下同时检查 reference、真实原生实现截图、并排图、50% 叠加图和差异图。用户明确确认前，不进入契约和后端阶段。

## 8. 交付顺序与上线门槛

- 场馆 membership 权限；
- 新增时段必须属于目标场馆与物理场地，时间对齐到 30 分钟且不能重叠；

- 价格与状态更新原子生效；
- 用户端读取结果与管理员保存结果一致。
