# 已授权场馆时区初始化设计

日期：2026-08-19

状态：用户已批准方案，等待规格复审

## 1. 问题与目标

平台审核通过场馆认领后，申请人已经获得有效的场馆管理权限，但目标场馆可能仍是仅目录展示的旧记录，`timezone` 为空。场馆资料和库存工作台均要求管理场馆使用 `Asia/Shanghai`，因此资料读取会返回 500，库存读取也无法工作。

目标是让所有已获得有效管理权限的中国境内场馆满足当前管理工作台的时区前置条件，同时不改变尚未被认领的普通目录场馆，也不放宽资料和库存接口的闭合契约。

## 2. 采用方案

### 2.1 新审核数据

- `CLAIM` 审核通过时，在授予或恢复 `VenueMembership` 前，将目标场馆时区规范为 `Asia/Shanghai`。当前管理工作台不支持其他时区，因此不能在保留 `UTC`、空字符串或其他非空异常值的同时发放有效管理权限。
- `CREATE` 审核通过时，新场馆直接以 `Asia/Shanghai` 创建。
- 会员资格逻辑、重复场馆判断、场馆的 `DIRECTORY_ONLY` 与 `is_listed` 状态均保持不变。

### 2.2 历史数据修复

新增 Alembic `0014` 数据迁移。升级时只更新同时满足以下条件的场馆：

- `venues.timezone IS DISTINCT FROM 'Asia/Shanghai'`，包括 `NULL`、空字符串和其他当前不支持的值；
- 至少存在一条 `is_active = true` 且 `can_manage_inventory = true` 的场馆会员关系。

未被授权管理的目录场馆继续允许时区为空或保留原值。数据修复不可安全恢复原始值，因此降级不把时区重新改回空值或其他旧值；降级只撤销迁移版本，不破坏已经变得可管理的数据。

## 3. 权威边界

`timezone` 是服务端管理工作台的场馆级权威数据。前端不添加默认值，资料 DTO 也继续要求 `Asia/Shanghai`。这样资料、场地配置、库存和履约页面使用同一个时区事实，不会出现资料页能打开但库存仍失败的局部修补。

本修复不把所有目录场馆强制改为上海时区，也不建设多时区能力。当前产品服务区域及既有接口只支持 `Asia/Shanghai`。

## 4. 错误与事务

认领或创建审核仍在原有审核事务内更新场馆与会员关系；任一步骤失败时整体回滚，不允许出现“权限已发放但管理必需字段仍为空”的新记录。

迁移使用集合更新且可重复判断。重复执行不会再次改写已经规范为 `Asia/Shanghai` 的场馆。

## 5. 聚焦验证

只新增与本缺陷直接相关的测试：

1. 认领时区分别为空和非上海值的场馆，审核通过后均规范为 `Asia/Shanghai`，会员权限仍正确；已有 `Asia/Shanghai` 保持不变。
2. 创建场馆审核通过后，新场馆时区为 `Asia/Shanghai`。
3. 从 `0013` 播种有效管理会员对应的空时区、非上海时区和上海时区场馆，以及没有有效管理会员的目录场馆；升级至 `0014` 后只把前两类管理场馆规范为上海时区。
4. 降级回 `0013` 后迁移版本正确，已规范的上海时区保持不变；同时更新仓库现有 migration head 断言为 `0014`。

随后运行平台入驻审核聚焦测试、迁移升级/降级及 migration head 聚焦测试、Ruff 与 diff check。部署测试环境后，用现有已认领场馆验证资料读取成功；场地配置读取也应成功。若场馆尚无物理场地，库存接口应从内部错误恢复为诚实的 `PITCH_NOT_FOUND`，使用现有“配置场地”工作台创建首个场地后再要求库存读取成功。本修复不为验收伪造物理场地或库存。

## 6. 不在范围内

- 前端页面或文案修改；
- 将时区字段改为可空响应；
- 全球多时区或场馆自选时区；
- 补建场馆图片、设施、物理场地或库存；这些内容仍由现有工作台按需创建。
