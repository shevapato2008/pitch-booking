## 1. 目标与边界

C1a 只闭环一条私域分享旅程：

```text
分享链接球局详情
→ 登录边界
→ 填写申请
→ 等待队长审核
→ 队长接受或婉拒
→ 申请人回到同一详情查看结果
```

今晚仅交付 development-only 的参考 Artifact、原生小程序 Fixture 和同尺寸视觉核对。所有成功结果都由同一隔离 store 的真实状态转换产生，不用 Toast、静态跳转或预写文案冒充业务成功。

本预览不会进入 production 包，不修改 B2 页面、生产路由、生产契约、后端、数据库、部署或体验版 `0.1.5`。明天用户确认视觉前，不以本设计冻结 API 或数据模型，也不宣称 C1a 已端到端完成。

## 2. 为什么采用这个子切片

### 方案 A：一次铺开完整 C1

同时做公开目录、三入口导航、申请、审核、候补、我的报名和订阅消息。页面与共享契约过多，并会争用仍在真机收口的 B2 public/manage 页面，不采用。

### 方案 B：只做公开目录

能够展示球局，却没有真实的申请结果，容易形成假入口，也不采用。

### 方案 C：私域分享申请闭环（采用）

在不启用“我要找球踢”的前提下，最小闭环申请人和队长两侧，并让接受与婉拒都能回读权威结果。公开发现、候补、我的报名和订阅消息分别留给 C1b/C1c。

独立范围裁决 Agent 已代用户批准方案 C、页面范围和状态语义；称呼来源是后续架构审计根据现有模型提出的最小建议，仍待用户明天一并确认。该批准只允许继续制作预览，不替代用户明天的视觉门。

## 3. 页面与入口

### 3.1 development-only 场景启动器

启动器明确显示“C1a 开发预览”，不模仿生产入口。它提供：

- 重置为未登录申请人；
- 进入接受分支或婉拒分支；
- 切换申请人 / 队长视角；
- 显示当前 Fixture 的身份、登录状态和报名状态。

启动器的按钮只重置或导航同一隔离 store，方便明天在一台设备上重复验证两条分支。它不进入 production manifest，也不代表真实用户可以切换角色。

### 3.2 申请人球局详情

复用 B2 公开详情已经确认的信息层级，但在独立 C1a 页面实现，不修改 B2 production 或 dev 页面。页面顺序：

1. 自定义导航与“开发预览”副标题；
2. “真实订场已确认”卡片：日期、时间、场馆和物理场地；
3. 球局名称、强度、位置需求、计划人数和真实剩余名额；
4. 预计 AA 与“到场线下结算，平台不代收或担保”；
5. 现有 B2 `team_name` 对应的组织者球队名、报名截止、装备和到场说明；
6. 报名状态区；
7. 尊重安全区的固定底部动作。

底部动作由当前身份与报名状态决定：

| 状态 | 底部动作 / 说明 |
| --- | --- |
| 未登录、可申请 | `登录并继续` |
| 已登录、可申请 | `申请加入` |
| `APPLIED` | 状态说明“等待队长审核”与真实 `刷新结果` |
| `JOINED` | “已加入本场球局”，不显示退出按钮 |
| `REJECTED` | “队长本次未能接受申请”，不显示重申请按钮 |
| 已满员 | “名额已满”，C1a 不显示候补按钮 |
| 暂停 / 已取消 / 已结束 | 对应只读说明 |

申请人始终从同一分享链接回到详情看结果，不新建结果页，也不增加“我的报名”假入口。

### 3.3 申请表

使用单列页面，字段都有可见标签：

- 本场称呼：必填，2–24 个可见字符。辅助文案明确“这是你在本场球局展示的称呼，不是微信昵称或实名”。现有 `User` 没有微信昵称或头像字段，因此不能假装自动取得微信展示身份；
- 意向位置：必选 `门将 | 后卫 | 中场 | 前锋 | 位置不限`，单选；
- 给队长的话：可选，最多 120 个字符，拒绝手机号、微信号、URL 等联系方式；
- “我已满 18 周岁”：必须主动勾选；
- “我了解足球运动存在受伤风险，并自愿参与”：必须主动勾选。

底部固定主操作是 `提交申请`，只有字段有效且两个确认均勾选时可用。`取消` 返回详情且不写报名。提交中禁止重复操作；若结果未知，保留输入和同一次 attempt，并把动作改为 `确认申请结果`，不能显示假成功。

### 3.4 队长报名审核

C1a 只显示一个合成的待审核申请，避免预览虚构列表基础设施。申请卡只包含：

- 申请人的自填称呼；
- 意向位置；
- 报名备注；
- 申请时间。

不显示头像、手机号、微信号、用户 ID、订单信息、履约场次或评分。当前系统没有可信的到场摘要，因此预览不伪造它。

`接受加入` 和 `婉拒` 分别打开有标题、结果说明、关闭和确认动作的底部确认层。确认后更新同一 Fixture 中的报名状态为 `JOINED` 或 `REJECTED`，审核页进入处理后空状态；切回申请人并重新进入详情时必须读取该状态。

## 4. Fixture 权威状态与转换

隔离 store 使用唯一标记 `C1A_PLAYER_APPLICATION_FIXTURE`，持有：

- `viewerRole: APPLICANT | CAPTAIN`；
- `authenticated: boolean`；
- `branch: ACCEPT | REJECT`，仅用于启动器说明和重复测试；
- `registrationStatus: NONE | APPLIED | JOINED | REJECTED`；
- 申请表快照、提交 attempt 和队长决策 attempt；
- 可注入的加载失败、结果未知和容量变化场景。

核心转换：

```text
NONE --submit--> APPLIED --accept--> JOINED
                         \--reject--> REJECTED
```

约束：

- 未登录只能触发 development-only 登录边界，不能直接写报名；
- 重复提交不能创建第二条报名；
- `APPLIED` 不占已加入名额；`JOINED` 才减少剩余名额；
- `JOINED` / `REJECTED` 都是终态，C1a 不提供退出、重申请或候补；
- 队长只能处理 `APPLIED`；处理后按钮消失；
- 容量在接受前变化时保持 `APPLIED`，显示“名额状态已变化”并提供真实刷新，不暗中转候补；
- `SUBMIT_UNKNOWN` / `MUTATION_UNKNOWN` 复用原 attempt 确认结果，不生成新 key。

## 5. 页面状态与错误语义

申请人详情覆盖：

- `LOADING`；
- `READY/APPLY_AVAILABLE`；
- `READY/APPLIED`；
- `READY/JOINED`；
- `READY/REJECTED`；
- `READY/FULL`；
- `READY/SUSPENDED|CANCELLED|COMPLETED`；
- `LOAD_ERROR`、`AUTH_LOSS`、`NOT_FOUND`。

申请页覆盖：

- `READY`、字段错误、`SUBMITTING`、`SUBMIT_UNKNOWN`；
- `STATE_CHANGED/FULL`、`AUTH_LOSS`、`NOT_FOUND`。

队长审核页覆盖：

- `LOADING`、`READY_PENDING`、`READY_EMPTY`；
- 接受 / 婉拒确认、`MUTATING`、`MUTATION_UNKNOWN`、`CAPACITY_CHANGED`；
- `LOAD_ERROR`、`AUTH_LOSS`、`NOT_FOUND`。

聚焦自动化覆盖所有状态转换；视觉门只拍核心旅程的代表状态，避免把简单预览扩张成全状态重拍。

## 6. 所有可见按钮的真实行为

| 按钮 | Fixture 行为 |
| --- | --- |
| 返回 | 返回真实上一页；无上一页时进入启动器 |
| 登录并继续 | 写入隔离登录态并停留在同一详情，随后展示申请动作 |
| 申请加入 | 进入申请表 |
| 位置 / 两项确认 | 更新可见表单值和校验结果 |
| 取消 | 放弃未提交的本次页面编辑并返回详情 |
| 提交申请 | 原子写入 `APPLIED` 后返回同一详情 |
| 确认申请结果 | 复用原 attempt 读取结果 |
| 刷新结果 | 重新从隔离 store 读取状态 |
| 接受加入 / 婉拒 | 打开对应确认层，不立即改状态 |
| 关闭确认层 | 关闭确认层且不改状态 |
| 确认接受 / 确认婉拒 | 写入 `JOINED` / `REJECTED`，进入审核空状态 |
| 启动器重置 / 角色切换 | 重置同一场景或导航对应视角 |

错误反馈以内联状态和可重试动作呈现；Toast 只可用于非权威的轻提示，不能承担任何成功结果。

错误与并发状态的动作也必须闭合：

| 状态 | 可见动作 | Fixture 行为 |
| --- | --- | --- |
| `LOAD_ERROR` | `重新加载`、`返回` | 重新读取同一资源；返回不改状态 |
| `AUTH_LOSS` | `重新登录并继续`、`返回详情` | 恢复隔离登录态后重新读取；若已有 attempt，只确认原 attempt |
| `NOT_FOUND` | `返回预览入口` | 返回启动器，不泄露或制造资源 |
| `STATE_CHANGED/FULL` | `返回球局详情` | 丢弃尚未提交的新输入，读取最新容量；不创建报名 |
| `SUBMIT_UNKNOWN` | `确认申请结果`、`返回详情` | 复用原申请 attempt；返回后详情仍可继续确认，绝不生成第二个 attempt |
| `MUTATION_UNKNOWN` | `确认审核结果`、`关闭` | 复用原决策 attempt；关闭不宣称成功，重新进入仍继续确认 |
| `CAPACITY_CHANGED` | `刷新报名列表` | 保持 `APPLIED` 并读取最新容量，不暗中接受或转候补 |

## 7. 视觉系统与参考帧

继续使用现有小程序设计系统，不采用工具给出的橙色营销主题或新字体：

- 背景 `#F8FAFC`，卡片 `#FFFFFF`；
- 主文字 `#10243E`，次文字 `#526479` / `#64748B`；
- 边框 `#DBE5EC`；
- 可信蓝 `#0284C7` / `#0369A1`；
- 仅在真实订场确认和 `JOINED` 使用语义绿 `#047857`；
- 婉拒使用中性说明，不用强烈错误红把正常队长决定表现为系统故障；
- 系统字体、4/8px 节奏、最小 44pt 触控区。

按钮、选项和关闭图标使用显式 flex 双轴居中；同组控件尺寸与列线一致。固定底栏为滚动区预留空间并包含 `env(safe-area-inset-bottom)`。不用 emoji 或伪造头像。

Artifact 在 `375 × 812` 提供六个代表帧：

1. `anonymous-detail`：分享详情与登录边界；
2. `application-ready`：称呼、位置、备注和两项确认；
3. `applied-detail`：等待审核与刷新；
4. `captain-pending`：待审核卡与双决策动作；
5. `joined-detail`：接受后的同一详情；
6. `rejected-detail`：婉拒后的同一详情。

development-only 启动器不作为产品参考帧，但在原生预览中人工检查可操作性。确认层只在代表性的接受分支核对一次，婉拒分支用同一组件和聚焦行为测试覆盖。

视觉门必须在同一个 `375 × 812` viewport 下，对六个代表状态各生成参考图与原生运行截图，并生成同尺寸并排图、50% 叠加图和差异图。人工记录至少核对：构图、几何间距、组件层级、字体色彩材质、图标完整性、关键文案和状态语义、按钮文字双轴居中、同组控件尺寸/列线、元素边界与裁切、固定底栏和安全区。发现一眼可见的问题先做最小修正；非阻塞差异记录即可，不扩大全状态重拍。

## 8. 隐私与文案边界

- 公开详情不出现订单号、手机号、微信号、完整名单或支付字段；
- 队长只见申请人主动提交的称呼、位置、备注和申请时间；
- 备注不承担私聊功能；
- 不出现“平台担保”“保证入选”“会收到通知”等尚未实现的承诺；
- 接受表示加入该场球局，不表示平台代收 AA 或保证到场；
- 婉拒是本场决定，不显示惩罚、信用或永久封禁语义。

Fixture 数据全部为合成数据，并在每个页面导航区标明“开发预览”。

## 9. 未来契约提示（非冻结）

视觉确认后再单独评审生产契约。为了兼容已经上传的 `0.1.5`，不得给现有 B2 closed DTO 增加报名或聚合字段；优先新增 registration context、apply、captain list 和 decision endpoint。

未来服务端必须：

- 使用当前 bearer session，不相信客户端角色；
- 让服务端投影 `can_apply/can_accept/can_reject` 和阻塞原因；
- apply/decision 使用 `Idempotency-Key` 与持久 attempt；
- 接受时在锁内重新统计 `JOINED`，容量冲突返回可刷新结果；
- 球局取消时把 `APPLIED/JOINED` 投影为取消状态，而不修改订单退款或场地库存；
- 新报名资源至少唯一约束 `(game_id, applicant_user_id)`，并保留版本和审计时间。

公开列表、候补、订阅消息和退出不属于 C1a，不能为了未来需求提前加表或抽象。

## 10. 隔离边界与删除条件

本分支只允许新增：

- `artifacts/ui/**` 下的 C1a 专属参考、流程、manifest 和评审资料；
- `miniprogram/dev/c1a-player-application-*`；
- `miniprogram/dev/pages/c1a-*/**`；
- C1a 聚焦测试与本设计 / 计划文档。

明确不修改：B2 Task 10 worktree 与验收记录、`backend/**`、迁移、OpenAPI、生产契约、`miniprogram/app.json`、`miniprogram/app.ts`、runtime/config、任何 production 或 dev `captain-game-*` 页面、B2 Fixture、`miniprogram/dev/bootstrap.ts`、`miniprogram/dev/app-pages.json`、中央 build/audit 脚本、deploy/live 配置及用户未跟踪文件。

production 构建必须与基线等价且不包含 `C1A_PLAYER_APPLICATION_FIXTURE`。后续只有在生产申请、审核、结果回读通过自动化和双账号真机验收后，才能删除本 Fixture；单账号只能证明视觉与隔离状态转换，不能宣称生产 E2E。

## 11. 最小验收

今晚预览阶段：

- 六个参考帧和对应原生状态在 375×812 可读且不被安全区遮挡；
- 六组参考图、原生运行截图、并排图、50% 叠加图和差异图均在相同 375×812 viewport 生成，并留下一轮人工视觉记录；
- 未登录、申请、等待、接受、婉拒均由同一 Fixture 状态转换产生；
- 所有可见按钮可导航、改变表单或改变权威 Fixture 状态；
- 接受与婉拒后，申请人从同一详情回读对应结果；
- 不显示假候补、假通知、假历史履约或假微信身份；
- production manifest/build 不含页面、路由或 Fixture 标记。

进入生产阶段的门槛：

- 用户确认参考与原生预览；
- B2 Task 10 完成真机收口和 Fixture 清理，不再存在共享文件争用；
- 独立契约评审完成，且真实验收可使用队长与申请人两个不同体验成员账号。

## 12. 明确不做

- 公开球局列表、日期 / 人制 / 剩余名额筛选和 PLAY 入口；
- 三入口底栏或通用导航重构；
- 我的报名、候补、FIFO 转正、退出、移除或到场记录；
- 订阅消息、通知 outbox、聊天或联系方式交换；
- 后端模型、迁移、API、worker、生产数据源和生产页面；
- 球队名册、头像、信用分、履约统计、平台内 AA 或支付；
- 修改、清理或重新上传 Task 10 体验版。
