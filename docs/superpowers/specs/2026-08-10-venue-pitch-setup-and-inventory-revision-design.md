# 物理场地配置与单场地库存工作台修订设计

**日期：** 2026-08-10

**状态：** 对话设计与书面规格已由用户确认，待 Reference Artifact 实现

**修订对象：** [目的入口与场馆单日库存切片设计](./2026-08-10-intent-entry-and-venue-inventory-design.md)

## 1. 结论

场馆库存旅程增加一个前置的“物理场地配置”页面。场馆工作人员先明确建立每一块可独立预订的真实场地，再进入单块物理场地的日期、时段和价格管理。

本设计修订原规格中把“7人场 / 5人场”直接当作两块物理场地标签的表达。场地制式只是一项属性；库存、时段、订单和冲突判断必须绑定唯一 `pitch_id`。

完整旅程为：

```text
已授权场馆工作人员
→ 打开场馆库存功能
→ 若尚无使用中的物理场地，进入物理场地配置
→ 逐块新增名称与制式并保存
→ 进入当前物理场地的单日库存
→ 切换日期或单块物理场地
→ 新增或编辑该场地的时段与价格
```

工作人员默认一次只操作一块物理场地。首期不提供把相同时段或价格批量应用到多块场地的能力。

## 2. 范围与优先级

本规格覆盖：

- 物理场地配置页；
- 单块场地的新增/编辑底部面板；
- 未填写名称时的稳定系统名称；
- 场地停用与删除规则；
- 库存页底部固定“新增时段”；
- 可扩展的当前物理场地选择器；
- “更多日期”月历底部面板；
- 日期与物理场地切换后的加载、错误和空状态；
- 开发 Fixture、同 viewport 视觉证据和删除条件。

本规格不覆盖：

- 多场地批量排班或批量定价；
- 周期模板、复制一周或拖拽排程；
- 场地平面图、组合场地或可拆分场地；
- 场馆资料 CMS、经营报表和审计后台；
- 普通商家自助注册或 membership 建设范围扩张。

本规格与原库存设计冲突时，以本规格为准。原规格中的权限、时段状态、重叠校验、幂等写入和 `checkout_version` 并发边界继续有效。

## 3. 已确认的方案与备选方案

### 3.1 库存页的物理场地切换

采用“当前场地单行入口 + 分组底部面板”：

- 库存页只显示当前物理场地，例如“A场 · 7人制”；
- 点击后打开“选择物理场地”底部面板；
- 面板按制式分组展示所有使用中的物理场地；
- 选择一块场地后关闭面板，保留当前日期并加载新场地的当天库存。

未采用横向滚动全部场地标签，因为六块及以上场地不能同时显示，末尾制式容易被隐藏。未采用“制式 + 编号”两级常驻标签，因为它持续占用两行高度，小屏首屏可见时段更少。

### 3.2 物理场地配置

采用“物理场地卡片列表”：

- 一块真实场地对应一张卡片；
- 卡片显示稳定展示名称、制式和状态；
- 点击卡片打开编辑面板；
- “添加一块场地”每次新增一条独立记录；
- 页面底部固定保存主操作。

未采用“先填写各制式数量”，因为后续减少数量时无法明确要删除或停用哪一块。未采用全部内联编辑，因为手机上的重复表单过重，删除操作也容易误触。

## 4. 页面层级与导航

### 4.1 首次配置

当场馆没有任何使用中的物理场地时，进入库存功能先显示配置页，不显示虚假的空库存列表。页面说明“每块可独立预订的场地都需要单独配置”。

配置页包含：

- 页面标题“配置物理场地”；
- 场馆名称；
- 已配置场地数量；
- 可纵向滚动的物理场地卡片列表；
- “添加一块场地”次级操作；
- 固定在底部安全区上方的“保存并设置时段”。

至少存在一块有效草稿并且所有草稿校验通过后，主操作才可提交。新增/编辑面板的主操作文案为“完成”，只把单块场地变更写入页面草稿；配置页底部主操作才提交整份配置。保存成功后进入规范排序第一块使用中的物理场地；全文唯一的规范排序是按 `players_per_side`、`sequence`、`id` 依次升序。

### 4.2 后续维护

库存页提供“场地配置”入口，进入同一个配置页维护已有场地。后续维护的底部主操作文案为“保存更改”；成功后返回库存页并尽量保持原 `pitch_id`。如果原场地已停用，则选择按规范排序第一块使用中的场地。

离开存在未保存修改的配置页前，显示二次确认。没有修改时使用正常返回行为。

## 5. 物理场地配置页

### 5.1 卡片内容

每张场地卡片显示：

- `display_name`；
- “自定义名称”或“系统生成名称”的来源提示；
- 制式标签，例如“7人制”；
- “使用中”或“已停用”的文字状态；
- 进入编辑面板的箭头。

首屏以理解和触控为优先，不在卡片中直接放删除或停用按钮。

尚未提交的新场地没有服务端 `sequence` 或 `system_name`。客户端为它生成只在本次草稿中有效的 `client_ref`。如果它也没有自定义名称，草稿卡片使用仅限本地的临时标签“新建的 7 人制场地 1”，末尾数字按当前页面内同制式未提交草稿的创建顺序生成，并显示来源提示“保存后生成正式名称”。临时标签不写入请求，也不参与服务端唯一性；请求携带 `client_ref`，成功响应回显 `client_ref → id / sequence / system_name` 映射并返回完整权威配置，从而原子替换临时记录。

从未产生业务数据的系统命名场地修改制式时，旧 `system_name` 在草稿中不继续冒充新制式名称。它同样显示上述新制式临时标签，直到保存响应返回目标制式的新稳定名称。填写了 `custom_name` 的草稿始终优先显示自定义名称。

### 5.2 新增与编辑面板

新增和编辑复用一个底部面板，包含：

- “场地名称”：可选，自定义名称在同一场馆内不可重复；
- “场地制式”：`5人制 / 7人制 / 8人制 / 11人制 / 其他`；
- “每队人数”：只有选择“其他”后在当前面板内原地展开；
- 把当前字段写入页面草稿的“完成”主操作；
- 对符合生命周期条件的已有场地显示删除或停用操作。

点击“其他”不打开第二层弹窗。它在当前面板内展开数字输入，使用数字键盘，输入 `1–99` 的整数并以“人制”为后缀，同时给出“预览：6人制”。保存后，预设与自定义人数都统一写入 `players_per_side`；客户端和服务端执行同一范围校验。

字段错误在字段下方就地展示；错误不关闭面板、不清空其他字段。

编辑面板不直接请求服务端。新增、修改、删除、停用和恢复都先形成页面级配置草稿；配置页底部“保存并设置时段”或“保存更改”使用一个 `Idempotency-Key` 把整份变更集原子提交。服务端在同一事务中验证并全部应用，任一项失败则整批不生效，不返回部分成功。

配置读取结果为每块场地提供权威能力快照：`can_edit_format`、`can_delete`、`can_deactivate`、`can_reactivate`、不可执行原因码，以及按 `AVAILABLE / LOCKED / BOOKED` 分类的未来阻塞数量。面板只根据该快照展示或禁用生命周期操作，不根据本地时段列表推断资格；提交时服务端再次校验，以处理读取后的并发变化。

保存超时或连接中断时，页面保持草稿并进入“正在确认保存结果”，使用原 `Idempotency-Key` 和完全相同的请求重试。只有获得权威成功响应才清除草稿并导航；明确失败时保留草稿并把错误定位到对应场地或字段。物理删除需要在草稿中加入操作前二次确认。

### 5.3 稳定名称

每块场地无论是否填写自定义名称，都获得不可回收的 `sequence` 和稳定 `system_name`。创建时，服务端按同场馆、同 `players_per_side` 分配下一个序号并生成 `system_name`，例如“7人场 · 2号场”。有效展示名称是 `custom_name ?? system_name`。

系统名称一经生成不因其他场地物理删除、停用或改名而自动重排。服务端为每个 `venue_id + players_per_side` 维护单调递增计数器；创建事务锁定对应计数器再分配序号，数据库唯一约束负责并发兜底。删除不会回退计数器，新场地始终使用历史已分配最大序号之后的下一个序号。

自定义名称长度为 1–30 个 Unicode 字素簇；保存时使用 NFC 规范化、去除首尾空白并把连续空白折叠为一个空格。唯一性比较使用该规范化值的 Unicode case-fold 结果。规范化后的有效展示名称在同一场馆所有未物理删除场地中唯一，也不能占用另一个场地的 `system_name`。生成系统名称时若候选值已被自定义名称占用，服务端继续分配下一个序号。名称和制式都不作为业务主键。

卡片和选择器中的单行长名称使用省略号截断，但场地编辑面板、时段编辑上下文和无障碍标签提供完整名称。

## 6. 场地生命周期

物理场地状态首期为：

- `ACTIVE`：可选择，可读取和新增未来库存；
- `INACTIVE`：不出现在正常库存选择器中，不允许新增库存，但历史库存与订单仍可查询。

删除与停用规则：

1. 从未产生时段、订单或其他业务记录的场地可以物理删除；
2. 已产生任何业务记录的场地不能删除，只能停用；
3. 场地仍有未来 `AVAILABLE`、`LOCKED` 或 `BOOKED` 时段时，服务端拒绝停用并返回按状态统计的待处理数量；未来 `CLOSED` 时段不阻止停用，并继续作为历史库存保留；
4. 工作人员处理完未来有效时段后才能再次停用；
5. 页面不能仅根据本地列表判断能否删除或停用，服务端是最终权威。

`INACTIVE → ACTIVE` 允许恢复，但服务端必须重新校验有效展示名称唯一性；成功后它重新进入库存选择器，已有 `CLOSED` 时段仍保持关闭。配置保存后必须至少保留一块 `ACTIVE` 场地；首期不承担“关闭整个场馆”的能力，因此停用最后一块使用中场地会被拒绝。

只有从未产生时段、订单或其他业务记录的场地可以修改 `players_per_side`。修改时从目标制式计数器分配新的 `sequence` 和 `system_name`，旧序号永不复用。已有业务数据后，制式在界面中只读；服务端仍以 `PITCH_FORMAT_IMMUTABLE` 拒绝绕过客户端的请求。需要改变制式时应新增一块场地，并按本节规则停用旧场地；任何已有时段始终绑定原 `pitch_id`，不迁移、不合并。

## 7. 修订后的库存工作台

### 7.1 固定区域与滚动区域

顶部不再放“新增时段”。页面结构为：

1. 场馆身份头部；
2. 月份和“更多日期”；
3. 当前自然周日期条；
4. 当前物理场地单行选择器；
5. 当前日期与时段数量摘要；
6. 可独立纵向滚动的当日时段列表；
7. 固定在底部安全区上方的“新增时段”主按钮。

底部操作栏必须包含设备安全区，列表底部必须预留操作栏的实际高度，最后一条时段不能被遮挡。底部面板打开时，页面主按钮位于遮罩下方且不可交互。

上方上下文保持稳定，但不能冻结过多内容导致 `375 × 812` 下列表失去有效浏览高度。实现以列表区域能独立滚动且日期、当前场地、底部主操作可持续辨认为准。

### 7.2 当前物理场地

当前场地选择器显示自定义名称或稳定系统名称，并同时显示制式。选择面板只展示 `ACTIVE` 场地，并使用全文统一的规范排序。

视觉上按 `players_per_side` 分组；分组从小到大，组内按 `sequence`、再按 `id` 排序。首次进入优先恢复仍为 `ACTIVE` 的最近一次 `pitch_id`；没有可恢复值时选择规范排序第一项。

选择新场地后：

- 当前日期不变；
- 摘要和列表进入加载状态；
- 只接受与最新 `venue_id + pitch_id + date + request_sequence` 一致的响应；
- 成功后更新时段数量和列表；
- 失败时保留当前选择并提供重试，不回退到旧场地数据。

### 7.3 “更多日期”

“更多日期”是有效操作，不再显示“仅视觉预览”提示。点击后打开自定义月历底部面板：

- 展示今天到今天后第 13 天，共 14 个可管理自然日；
- 其他日期可用于理解自然周位置，但使用禁用样式、不可点击，也不能成为待确认日期；
- 选择日期后先在月历中高亮，并显示完整日期；
- 点击“确认日期”关闭面板并更新库存页；
- 关闭或取消不改变库存页当前日期。

确认日期后不跳转新页面。库存页日期条更新为所选日期所在自然周的周一至周日，所选日期高亮；当前物理场地保持不变，摘要和时段列表读取新日期数据。例如选择 8 月 23 日后，日期条显示 8 月 17–23 日并高亮 23 日。

直接点击当前周日期条中的可管理日期时可立即更新，无需再次确认。

### 7.4 新增时段

底部“新增时段”始终绑定当前 `pitch_id` 和当前日期。打开面板时上下文标签必须同时显示日期、物理场地名称、制式和草稿时间，避免工作人员误改其他场地。

新增和编辑时段继续遵循原库存设计的权限、30 分钟粒度、半开区间、重叠、锁定、已售、幂等和并发版本规则。

## 8. 数据模型与权威边界

最小物理场地模型：

```text
VenuePitch
  id: immutable pitch_id
  venue_id: owning venue
  custom_name: nullable staff-provided name
  system_name: stable stored fallback name
  players_per_side: integer from 1 through 99
  sequence: stable sequence within venue and format
  status: ACTIVE | INACTIVE
```

`display_name` 是只读派生值 `custom_name ?? system_name`，不再作为第三份可独立修改的数据存储。数据库身份和关联始终使用 `id`，不能使用名称或制式。

库存查询键为：

```text
venue_id + pitch_id + local_date
```

切换日期保留 `pitch_id`；切换场地保留 `local_date`。时段、价格、锁定状态、订单和重叠约束都落在唯一 `pitch_id` 上，而不是 `players_per_side`。

客户端 Fixture 只提供开发态页面需要的场地、日期和状态数据。后端接入后，场地列表、名称、状态、可停用性、单日库存和保存结果都以服务端为权威。

### 8.1 与现有 `pitch_type` 的兼容迁移

当前数据库和用户端可订契约把 `pitch_type` 限定为 `FIVE_A_SIDE | SEVEN_A_SIDE`。本修订以数值 `players_per_side` 作为后续唯一权威，并在契约/后端阶段按以下顺序迁移：

1. 为现有 `pitches` 增加 `players_per_side`、`system_name`、`custom_name`、`sequence` 和 `status`；`FIVE_A_SIDE → 5`、`SEVEN_A_SIDE → 7`，现有 `name` 作为首批稳定 `system_name`，按现有 `sort_order`、再按 `id` 分配稳定序号；
2. 用户端场馆详情把可订制式改为使用中物理场地的不同 `players_per_side` 集合，标签统一为“`${players_per_side}人制`”；
3. 用户端可订查询和响应改用 `players_per_side`，返回每块使用中物理场地的 `pitch_id`、有效展示名称和数值制式；`INACTIVE` 场地不进入普通场馆详情与可订响应；
4. 旧 `pitch_type` 查询在迁移期只作为 `5/7` 的兼容适配入口，并投影到数值查询；`8/11/其他` 只由更新后的数值契约与客户端公开展示；
5. 同一发布切片必须先部署兼容服务端，再部署数值客户端，最后才允许管理员把非 5/7 场地设为 `ACTIVE`；旧枚举字段的最终移除另行迁移，不阻塞本切片验收。

兼容期的新场地同时满足现有数据库列约束：

- `code`：服务端生成不透明且稳定的 `pitch_<uuid-hex>`，现有记录保持原值；
- `name`：事务内镜像当前有效展示名称，供旧读取路径兼容，名称修改时同步更新；
- `sort_order`：按场馆维度使用历史最大值加一并永久保留，旧 5/7 查询继续得到稳定顺序；
- `pitch_type`：迁移为可空兼容列，`5 → FIVE_A_SIDE`、`7 → SEVEN_A_SIDE`，其他人数写入 `NULL`；旧查询只匹配非空兼容值，新数值查询不读取该列作为权威。

数据库迁移在写入非 5/7 场地前先放宽 `pitch_type NOT NULL`，相关枚举 DTO 和旧服务只维持 5/7 兼容投影。这样 8/11/自定义场地可以持久化，而不会伪造一个错误的旧枚举值。

`DIRECTORY_ONLY` 场馆的人工 `public_pitch_types` 继续属于目录资料，不由物理场地配置页修改。只有 `ONLINE` 场馆的公开可订制式从 `ACTIVE` 物理场地派生。

## 9. 页面状态与错误处理

### 9.1 场地配置

至少覆盖：

- 首次加载；
- 加载失败和“重新加载”；
- 尚无场地；
- 正常场地列表；
- 新增场地面板；
- 编辑场地面板；
- “其他”人数输入；
- 保存中；
- 字段校验失败；
- 保存失败且草稿保留；
- 保存结果未知并使用原幂等键确认；
- 停用被未来有效库存阻止；
- 删除前二次确认、删除成功、停用成功和恢复成功；
- 存在未保存修改时的离开确认。

保存期间禁用重复提交。网络或服务失败时不清空草稿；允许使用同一用户动作语义重试。服务端返回名称冲突、非法人数、非法制式、场地存在业务历史或仍有未来有效库存时，页面显示对应原因，不统一伪装成普通保存失败。

读取配置时服务端返回 `configuration_version`，保存时提交 `expected_version`。其他管理员已更新配置时返回 `409 CONFIGURATION_CHANGED` 和最新权威配置；客户端保留本地草稿，停止自动提交并提示“场地配置已变化，请重新核对”，由工作人员查看差异后重新应用。网络结果未知仍使用原幂等键和原 `expected_version` 确认，不生成新操作。

服务端处理保存请求时必须先按用户、operation 和 `Idempotency-Key` 查询重放记录，再校验当前 `configuration_version`。因此一次已经提交成功但响应丢失的请求，即使随后配置又被其他管理员更新，仍能重放原成功结果；只有首次处理该键时才执行 `expected_version` 校验。

### 9.2 库存工作台

至少覆盖：

- 当前场地与日期的列表加载；
- 加载失败和“重新加载”；
- 无当日时段及“新增时段”；
- 场地选择面板；
- 日期选择面板；
- 可独立滚动的长时段列表；
- 新增/编辑时段；
- 保存中；
- 保存结果未知；
- 新增时段重叠；
- 并发状态变化；
- 权限失效。

切换场地或日期只替换摘要和列表区域，不清空页面身份上下文。快速连续切换时只接受最后一次请求；迟到响应必须丢弃。加载失败不能显示成“0 个时段”。

## 10. 前端边界与 Fixture

保持四个可独立理解的前端边界：

1. 物理场地配置页：读取权威版本，持有完整变更集草稿、原子提交幂等键和保存状态；
2. 物理场地编辑面板：只校验名称、预设/自定义人数和生命周期操作，并把一块场地的变化写回页面草稿；
3. 库存工作台：持有当前日期、当前 `pitch_id`、月历/选择器和单日列表；
4. 服务端口：提供读取带版本的场地配置、以 `expected_version + Idempotency-Key` 原子保存变更集、读取单日库存和单时段写入。

开发态 Fixture 与未来生产 HTTP 适配器实现相同页面端口，但生产构建只能注册 HTTP 适配器。Fixture 必须位于现有开发组合根，不得进入生产包。

Fixture 删除条件为：物理场地配置、真实场地列表、单日库存和时段写入后端全部集成，真实设备/用户验收通过，且生产包审计确认没有模拟业务数据。

## 11. 视觉与交互规则

沿用现有小程序视觉语言：浅色背景、白色表面、深蓝主文本、信任蓝主操作、明确的成功/注意/只读文字状态和系统字体。

必须满足：

- `375 × 812` 作为主要对比 viewport；
- 触控区域至少 `88rpx`；
- 固定底部操作栏适配设备安全区；
- 按钮文字和图标在按钮内几何居中；
- 图标使用统一 SVG 或原生绘制，不使用 emoji；
- 所有箭头、关闭图标和状态图标完整位于组件边界内；
- 状态不能只靠颜色表达；
- 字段有可见标签，错误靠近对应字段；
- 底部面板不叠加第二个底部面板；
- 列表滚动不带动固定底部主操作；
- 禁用日期、禁用操作和只读库存使用文字说明语义。

## 12. 视觉证据与测试

两个页面分别建立 Reference Artifact 与原生 Fixture 证据。场地配置页至少覆盖：

1. 没有使用中场地的首次入口；
2. 添加第一块场地；
3. 保存成功并进入该场地库存；
4. 六块物理场地列表；
5. 编辑预设制式场地；
6. 编辑“其他”制式并输入人数；
7. 停用被未来库存阻止；
8. 未使用场地删除成功并从草稿消失；
9. 已有场地停用成功、恢复成功；
10. 保存失败或结果未知且草稿保留。

修订后的库存页至少覆盖：

1. 单日库存与底部固定“新增时段”；
2. 场地选择面板；
3. 更多日期月历；
4. 选择跨周日期后的新周视图；
5. 长列表滚动到最后一项；
6. 新增时段面板；
7. 保存结果未知；
8. 新增时段重叠。

每个主要状态在同一个 `375 × 812` viewport 下检查：

- Reference；
- 真实微信小程序实现截图；
- 并排图；
- 50% 叠加图；
- 差异图。

视觉记录必须逐项说明构图、几何间距、组件层级、字体色彩材质、图标素材、文案和状态语义差异。自动化布局测试通过不等于视觉通过；用户明确确认前不得进入契约或后端阶段。

前端自动化保持轻量，重点覆盖：

- 场地草稿与名称生成展示；
- 预设/自定义人数切换；
- 删除与停用状态映射；
- 当前日期与 `pitch_id` 的独立保持；
- 迟到读取响应丢弃；
- 底部面板状态转换；
- Fixture 与生产构建隔离。

## 13. 交付顺序

遵循单一在制品和用户旅程垂直切片：

1. 修订库存 Artifact，并新增物理场地配置 Artifact；
2. 由用户确认 Reference；
3. 使用隔离 Fixture 实现场地配置原生页面；
4. 完成同 viewport 视觉证据并取得用户确认；
5. 修订并实现库存原生页面；
6. 完成同 viewport 视觉证据并取得用户确认；
7. 冻结物理场地与库存契约；
8. 实现场地配置、生命周期和库存后端；
9. 前后端集成并验证用户端按真实 `pitch_id` 读取库存；
10. 完成自动化、真实设备和用户验收；
11. 删除 Fixture，并审计生产包无模拟业务数据。

首个实现计划仍停在前端视觉门槛，不创建生产路由、后端端点或数据库迁移。
