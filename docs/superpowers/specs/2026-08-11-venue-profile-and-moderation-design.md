# 场馆资料、设施标签与内容审核设计

**日期：** 2026-08-11

**状态：** 用户已确认设计，书面规格审查通过，实施计划已编制

**关联设计：**

- [目的入口与场馆单日库存切片设计](./2026-08-10-intent-entry-and-venue-inventory-design.md)
- [物理场地配置与单场地库存工作台修订设计](./2026-08-10-venue-pitch-setup-and-inventory-revision-design.md)

## 1. 目标与结论

为已获授权的场地方新增独立“场馆资料”页面，用于维护：

1. 场馆级图片；
2. 不超过 300 字的场馆介绍；
3. 固定白名单中的设施和场地特征标签。

图片和介绍必须审核通过后才能发布。设施标签是客观结构化选项，不进入内容审核。用户端场馆详情只读取已发布资料，不展示联系电话、拨号入口、聊天入口、外链或其他可帮助绕过平台交易的内容；核心操作是查看实时低价时段并在平台内下单锁定。

首期只维护场馆级图片，不把图片关联到具体物理场地。物理场地数量、名称和人数制式继续由“配置场地”页面维护；日期、时段和价格继续由库存工作台维护。

## 2. 采用与不采用的方案

采用“单项即时审核、整版自动发布”：

- 新图片上传成功后立即独立审核；
- 场馆介绍保存后立即独立审核；
- 所有属于当前草稿版本的待审核项目通过后，后台原子发布新版介绍和整套图库；
- 审核期间用户端继续展示旧版；
- 设施标签在“保存资料”的原子请求中独立生效，不等待内容审核。

不采用统一点击“提交审核”的批量模式，因为一项失败会推迟所有反馈。不采用所有内容都转人工审核，因为当前阶段会引入不必要的等待和运营成本。不开放自定义标签，避免同义词、营销词和不可筛选数据。

## 3. 页面与导航

场地方工作台提供三个并列入口：

- 场馆资料：介绍、设施标签、场馆图片和审核状态；
- 配置场地：物理场地数量、自定义名称和人数制式；
- 库存时段：每块物理场地的日期、时段、价格和开放状态。

“场馆资料”使用独立页面，不把内容编辑器塞入“配置场地”。页面沿用已经确认的小程序设计系统和运行时安全区布局，不引入新的营销视觉主题。

### 3.1 场馆资料页

页面从上到下包括：

1. 自定义导航标题“场馆资料”；
2. 与主标题同等清晰的场馆名称；
3. 发布状态摘要：“已发布”“审核中”或“部分内容未通过”；
4. 场馆图片区；
5. 场馆介绍区；
6. 分组设施标签区；
7. 固定底部“保存资料”按钮。

“保存资料”通过一个原子写请求同时保存介绍草稿和设施标签：标签在请求成功后直接生效，介绍发生变化时在同一事务内创建持久审核任务。任一版本冲突或校验失败时两部分都不写入，因此页面不会出现“标签已生效但介绍保存失败”的部分成功。图片上传、删除、排序和设为封面在图片区即时提交真实请求，不等待底部按钮重复上传。

### 3.2 用户端场馆详情

用户端展示：

- 已发布封面和图库；
- 已发布设施标签；
- 已发布场馆介绍；
- 实时价格、可订状态和“查看可订时段”主操作。

用户端不展示联系电话、拨号按钮、平台内聊天、二维码、外链或线下付款提示。场馆电话可以继续作为平台内部运营资料保存，但必须从所有公开场馆详情响应以及订单详情中的场馆 `customer_service_phone` 字段移除，同时删除对应解码器、视图模型和用户界面入口。用户为下单验证的手机号及订单中的用户脱敏手机号属于履约身份信息，继续保留，不属于场馆联系方式。平台不主动提示用户去第三方地图查找电话。

## 4. 图片规则

- 每个场馆最多 8 张已发布或当前草稿目标图片，其中恰有 1 张封面；
- 支持 JPEG、PNG 和 WebP，单张最大 10 MB；
- 支持上传、删除、排序和设为封面；
- 图片只属于场馆，不关联物理场地；
- 上传完成后单张立即进入审核，不阻塞继续上传其他图片；
- 审核中的新图片不公开；
- 替换已发布图片时，旧图库继续公开，直到当前草稿整版通过；
- 删除封面前必须先指定新封面；草稿不能形成无封面的可发布版本；
- 审核使用压缩副本，发布保留合格原图；
- 相同文件哈希可复用仍有效的审核结论，避免重复模型调用；
- 未通过和废弃的私有临时文件按平台保留期限清理。

创建新草稿时，当前已发布图片以只读引用进入草稿并继承既有通过结论，不复制对象，也不重新审核。只调整排序、封面或删除既有图片时不触发模型；只有上传了新文件才创建图片审核任务。

图片状态为：

- `UPLOADING`：客户端仍在上传；
- `REVIEWING`：审核任务处理中；
- `APPROVED`：单项已通过，等待整版发布；
- `REJECTED`：未通过，可删除或重新上传；
- `PENDING_MANUAL`：模型不确定或自动重试耗尽，等待人工处理。

上传网络失败不创建审核任务，页面保留其他编辑内容并显示“上传失败，请重试”。

## 5. 场馆介绍规则

- 普通文本，最多 300 个 Unicode 码点，允许换行；前端使用 `Array.from(text).length`，后端使用 Python `len(text)`，保持同一计数规则；
- 页面持续显示已用字数和上限；
- 不支持富文本、电话号码、微信号、二维码、外部链接或收款信息；
- 保存后立即审核；
- 审核中的介绍不公开；
- 未通过时显示固定原因并保留输入，允许修改后重新保存；
- 新介绍通过前，用户端继续展示旧介绍。

## 6. 设施与场地特征标签

标签是固定代码和固定中文名，不允许场地方输入自定义值。首期标签分组如下：

| 分组 | 代码 | 展示名称 |
| --- | --- | --- |
| 基础设施 | `PARKING` | 停车场 |
| 基础设施 | `TOILET` | 卫生间 |
| 基础设施 | `CHANGING_ROOM` | 更衣室 |
| 基础设施 | `SHOWER` | 淋浴 |
| 基础设施 | `LOCKERS` | 储物柜 |
| 补给服务 | `DRINKING_WATER` | 饮水设施 |
| 补给服务 | `BEVERAGE_SALES` | 饮料售卖 |
| 补给服务 | `EQUIPMENT_RENTAL` | 器材租赁 |
| 观赛与安全 | `REST_AREA` | 休息区 |
| 观赛与安全 | `FIRST_AID` | 急救设施 |
| 观赛与安全 | `AED` | AED |
| 场地环境 | `INDOOR` | 室内 |
| 场地环境 | `OUTDOOR` | 室外 |
| 场地环境 | `COVERED` | 有顶棚 |
| 场地环境 | `LIGHTING` | 夜场照明 |
| 草皮类型 | `ARTIFICIAL_TURF` | 人工草 |
| 草皮类型 | `NATURAL_GRASS` | 天然草 |

一个场馆可以同时具有室内和室外、人工草和天然草，含义均为“该场馆至少有一块符合条件的场地”。未来若增加单块场地资料，再把相关属性细化到具体物理场地。

五人制、七人制等人数制式不作为人工标签重复维护，用户端从已启用的物理场地配置自动生成。

## 7. 审核结果与固定文案

审核提供者只能返回结构化状态、固定原因码和置信度，不得把模型自由文本直接展示给用户。

| 原因码 | 前端固定文案 |
| --- | --- |
| `CONTACT_INFO` | 请删除电话、微信号等联系方式 |
| `QR_OR_PAYMENT_CODE` | 图片中不能包含二维码或收款码 |
| `OFF_PLATFORM_TRADE` | 请删除线下交易或绕过平台付款的引导 |
| `EXTERNAL_LINK` | 请删除外部网站或其他平台链接 |
| `UNRELATED_CONTENT` | 内容需与当前场馆有关 |
| `IMAGE_NOT_VENUE` | 请上传真实的场馆环境照片 |
| `IMAGE_QUALITY` | 图片过于模糊或无法辨认 |
| `PERSONAL_PRIVACY` | 图片包含清晰人物面部或其他隐私信息 |
| `UNSAFE_CONTENT` | 内容不符合平台发布要求 |

审核通过返回 `PASS`。模型无法可靠判断时返回 `UNCERTAIN`，系统保持“审核中”并自动重试；超过有限重试次数后转为 `PENDING_MANUAL`，不直接驳回，也不发布。

人工兜底只建设最小内部能力，不建设通用运营后台。平台在部署配置中维护一组审核员用户 ID；只有这些已登录用户可以读取人工待审项目和私有审核副本，并提交 `PASS` 或上述固定拒绝原因码。人工决定必须记录审核员、时间和决定。`PENDING_MANUAL → APPROVED` 后立即重新检查整版发布条件；`PENDING_MANUAL → REJECTED` 后保留草稿并向场地方展示对应固定文案。其他用户不能访问人工审核接口。

成本控制规则：只审核变化的介绍和新增图片；描述使用单次短请求；每张图片使用一份压缩审核副本和一次结构化请求；使用哈希复用有效结果；不与模型进行多轮对话。

## 8. 数据边界与发布事务

现有 `Venue.description`、`VenueImage` 和 `VenueFacility` 继续作为公开已发布资料的权威来源。新增草稿和审核边界：

- `VenueProfileRevision`：场馆、草稿版本、基础已发布版本、目标介绍、整体状态、创建者和时间；
- `VenueProfileImageDraft`：所属草稿版本、私有对象键、角色、排序、哈希和审核状态；
- `ContentModerationJob`：审核项目类型、项目版本、尝试次数、下一次执行时间、状态和固定原因码。

每个场馆最多存在一个当前可编辑草稿。审核中继续编辑会递增草稿版本；旧版本迟到的审核结果必须丢弃，不能发布已被用户替换的内容。

发布器只在以下条件同时满足时工作：

- 当前草稿仍是场馆最新草稿；
- 介绍若变化则已通过；
- 所有目标图片已通过；
- 图片不超过 8 张且恰有一张封面；
- 草稿基于的已发布版本仍未变化。

满足条件后，发布器在一个数据库事务内替换 `Venue.description` 和该场馆的 `VenueImage` 集合，递增发布版本，并把草稿标记为已发布。任一条件不满足时不修改公开资料。

设施标签继续写入现有 `VenueFacility` 权威表并在“保存资料”请求提交后立即生效，不等待图片或介绍审核。该请求同时携带期望设施版本和期望草稿版本；服务端在一个事务内校验两个版本、更新设施、更新介绍草稿并写入审核任务 outbox，任一环节失败则整体回滚，避免多个场馆工作人员互相覆盖或产生部分成功。

## 9. 接口与按钮真实性

场馆资料服务端口至少提供以下真实能力：

- 读取当前已发布资料、设施和当前草稿；
- 原子保存 300 码点以内的介绍草稿和白名单设施标签，并在介绍变化时触发审核；
- 上传一张场馆图片并触发审核；
- 删除一张草稿图片；
- 调整草稿图片顺序；
- 设置草稿封面；
- 对系统审核失败的项目请求重新审核；
- 读取最新审核和发布状态。

平台人工审核服务端口另提供两个受限能力：读取 `PENDING_MANUAL` 队列，以及对单个仍为当前草稿版本的项目提交 `PASS` 或固定拒绝原因码。人工审核提交也必须幂等，并拒绝已经被新草稿替换的项目。

HTTP 接口位于场馆管理员命名空间，复用 `VenueMembership.can_manage_inventory` 作为当前最小场馆管理权限；普通用户和其他场馆成员不能读取私有草稿或修改资料。写操作使用 `Idempotency-Key` 和期望草稿或设施版本，未知结果必须使用原键确认，不能重复创建图片或审核任务。

小程序的上传、删除、排序、设为封面、保存和重试操作必须分别绑定上述真实能力；返回操作只执行真实页面导航并保留已确认的未保存提示。生产构建不得注册 Fixture 数据源或伪造审核成功。

审核模型通过窄接口 `ContentModerationProvider` 接入。首期生产适配器使用阿里云百炼 DashScope，从进程环境读取 `DASHSCOPE_API_KEY`，密钥不得写入仓库、日志或响应。图片审核默认使用具备视觉输入和结构化输出能力的低成本动态模型别名 `qwen3-vl-flash`，以非思考模式调用；模型名和百炼兼容接口 Base URL 使用部署环境配置，便于价格或可用性变化时替换而无需修改业务代码。根据 2026-08-11 的阿里云官方资料，该模型接受文本和图片输入，在华北 2 区域不超过 32K 输入时原价为每百万输入 Token 0.15 元、输出 Token 1.5 元。审核副本在保持文字可识别的前提下降低分辨率，并把输出限制为短 JSON。

业务层只依赖结构化输入输出，不依赖具体模型供应商 SDK。持久化审核任务由后台工作进程领取，有限自动重试后进入人工队列。

## 10. 失败处理

| 情况 | 页面行为 | 服务端行为 |
| --- | --- | --- |
| 页面读取失败 | 保留页面框架并提供“重新加载” | 不返回其他场馆资料 |
| 图片上传失败 | 保留其他输入，显示“上传失败，请重试” | 不创建审核任务 |
| 内容未通过 | 缩略图或文本旁显示固定原因 | 保留私有草稿，不修改公开资料 |
| 审核暂时失败 | 显示“审核中” | 有限自动重试，随后转人工 |
| 并发版本变化 | 提示资料已更新，刷新最新草稿 | 拒绝覆盖并返回当前版本 |
| 权限失效 | 退出编辑态 | 拒绝读取私有草稿和所有写入 |
| 写入结果未知 | 保留操作状态并允许确认结果 | 使用原幂等键重放权威结果 |
| 发布事务失败 | 继续展示旧版 | 整体回滚，不产生半发布图库 |

## 11. 交易防绕行边界

公开地图可以提供场馆电话，因此平台不能承诺彻底阻止用户在线下找到场馆。首期目标是平台不主动帮助绕单，并通过真实库存、低价时段、即时锁定、订单凭证、退款和售后价值降低绕单动机。

- 用户端不展示场馆联系电话，支付后也不展示；主要场馆、在线场馆、目录场馆的公开详情都删除 `phone`，订单详情删除场馆 `customer_service_phone`；
- 用户自身的登录/下单手机号验证和订单中的用户脱敏手机号保持不变；
- 首期不建设场馆聊天，订单问题进入平台售后；
- 场馆介绍和图片审核阻止联系方式、二维码、外链和线下交易引导；
- 平台采用较低交易服务费，避免用过高佣金强化场地方绕单动机；
- 场地方合作规则禁止主动诱导绕单，重复违规可提醒、降权或暂停发布；
- 实时低价和剩余库存必须来自权威数据，不使用虚假倒计时或虚假紧迫提示。

## 12. 轻量验收

只覆盖当前旅程的关键风险，不扩展通用审核平台或无关防御测试。

后端聚焦验证：

- 场馆权限和跨场馆隔离；
- 图片数量、格式、大小、唯一封面和设施白名单；
- 介绍长度；
- 固定审核结果解码；
- 迟到审核结果丢弃；
- 自动重试转人工；
- 原子整版发布；
- 幂等上传和写入；
- 主要场馆、在线场馆、目录场馆公开详情不含场馆 `phone`，订单详情不含场馆 `customer_service_phone`，但用户脱敏手机号契约保持不变；
- 用户端只读取已发布资料。

前端聚焦验证：

- 每个可见按钮调用对应服务能力；
- 上传、审核中、已通过、未通过、人工待审和读取失败状态；
- 300 字限制、最多 8 张、封面约束和标签分组；
- 用户端删除电话和拨号入口。

在真实微信开发者工具的 `375 × 812` viewport 进行交付前视觉自审，重点检查图片网格、标签、字数提示、审核状态、按钮文字居中、关闭和箭头图标、固定底部按钮及安全区。真实联调至少完成一次通过图片、一次拒绝图片、一次介绍审核和一次设施保存。对象存储、真实审核模型、后台工作进程和小程序合法域名均配置完成后，才允许用户端读取新版资料。

## 13. 非目标

首期不包含：

- 单块物理场地图片和介绍；
- 自定义设施标签；
